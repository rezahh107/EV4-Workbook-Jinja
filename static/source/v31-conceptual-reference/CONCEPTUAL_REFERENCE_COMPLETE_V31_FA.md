# ۱. درک عمیق Elementor V4؛ واقعاً چگونه فکر می‌کند؟

## مسئله‌ای که این مفهوم حل می‌کند

مبتدی معمولاً Elementor را مجموعه‌ای از دکمه‌ها می‌بیند:

- اینجا رنگ را عوض کن.
- آنجا فاصله بده.
- این گزینه را روی Row بگذار.
- اگر درست نشد، Margin اضافه کن.

این روش ممکن است یک صفحه را ظاهراً درست کند، اما ذهن طراح را وابسته به آزمون‌وخطا نگه می‌دارد. با اضافه‌شدن هر Element جدید یا تغییر اندازهٔ صفحه، دوباره همه‌چیز مبهم می‌شود.

مشکل اصلی کمبود کنترل نیست؛ **نبودن مدل ذهنی** است.

---

## تشبیه به دنیای واقعی: ساختن یک شهر

Elementor V4 را مثل ساختن یک شهر تصور کن:

- **Element** = ساختمان، تابلو، پل یا فضای سبز
- **Element Tree** = نقشهٔ خیابان‌ها و رابطهٔ محله‌ها
- **Display و Layout** = قانون حرکت و نحوهٔ توزیع فضا
- **Class** = آیین‌نامهٔ ظاهری یک گروه از ساختمان‌ها
- **Variable** = دفتر مرکزی مقادیر مشترک، مثل رنگ رسمی یا فاصلهٔ استاندارد
- **Component** = ساختمانی با نقشهٔ مادر که در چند محله تکرار می‌شود
- **State** = وضعیت موقتی یک بخش هنگام تعامل
- **Responsive Rule** = مقررات شهر برای زمین‌های کوچک‌تر

اگر فقط نمای ساختمان را رنگ کنی اما خیابان اشتباه باشد، شهر درست کار نمی‌کند.

---

## تعریف دقیق با زبان ساده

مدل فکری درست در V4 این ترتیب را دارد:

```text
معنا و نقش
↓
ساختار و رابطهٔ Parent/Child
↓
موتور چیدمان
↓
اندازه و فاصله
↓
Style و State
↓
قواعد قابل‌استفادهٔ مجدد
↓
Responsive و آزمون نهایی
```

یعنی قبل از اینکه بپرسی «چه رنگی باشد؟» باید بپرسی:

> این Element چیست و چرا در این نقطه از Tree قرار گرفته است؟

Elementor V4 استفاده از Elementهای اتمیک، پنل Style استانداردتر و ویرایش Classمحور را پررنگ کرده است. در مستندات رسمی، هر Element حداقل یک Local Class دارد و Styleهای قابل‌استفادهٔ مجدد می‌توانند در Global Classها نگه‌داری شوند.

---

## چرا V4 به این سمت طراحی شده است؟

در یک سایت کوچک، تغییر دستی ده دکمه شاید قابل تحمل باشد. در یک سایت واقعی با ده‌ها صفحه، این روش سه مشکل می‌سازد:

1. **عدم یکنواختی:** هر دکمه کمی با دیگری فرق می‌کند.
2. **هزینهٔ تغییر:** تغییر برند باید در ده‌ها نقطه انجام شود.
3. **ابهام در خطا:** معلوم نیست Style از کجا آمده است.

V4 می‌خواهد تصمیم‌ها از حالت «تنظیم پراکنده» به «سیستم قابل ردیابی» نزدیک شوند.

---

## رفتار را قدم‌به‌قدم دنبال کن

فرض کن باید یک Hero بسازی.

### مرحلهٔ ۱: نقش‌ها را جدا کن

```text
Hero Shell
├── Copy Group
│   ├── Eyebrow
│   ├── Heading
│   ├── Paragraph
│   └── Actions
└── Visual Group
    └── Image
```

هنوز رنگ و Padding مهم نیست. ابتدا باید معلوم شود هر چیز چه نقشی دارد.

### مرحلهٔ ۲: Parent مشترک را درست کن

Copy و Visual باید کنار هم قرار بگیرند؛ پس Parent آن‌ها باید موتور چیدمان مناسبی داشته باشد.

### مرحلهٔ ۳: موتور چیدمان را انتخاب کن

برای دو گروه کنار هم معمولاً Flex Row کافی است. اگر جای‌گذاری دقیق در چند ردیف و ستون لازم باشد، Grid بررسی می‌شود.

### مرحلهٔ ۴: اندازه و فاصله را تعریف کن

ابتدا Width/Basis و سپس Gap/Padding. Margin نباید جای ساختار اشتباه را بگیرد.

### مرحلهٔ ۵: Style را در محل درست قرار بده

- استثنای یک Element → Local Class
- الگوی تکراری → Global Class
- مقدار مشترک → Variable
- ساختار تکراری چندعنصری → Component

### مرحلهٔ ۶: Responsive Contract را تعیین کن

مثلاً:

```text
Desktop: Row، تصویر 45٪
Tablet: Row فشرده یا Column
Mobile: Column، متن و دکمه تمام‌عرض
```

---

## در Elementor V4

وقتی Element را انتخاب می‌کنی، به‌جای حرکت تصادفی میان کنترل‌ها، این پرسش‌ها را به‌ترتیب پاسخ بده:

1. این Element محتوایی است یا فقط Wrapper؟
2. Parent آن چیست؟
3. Display و Layout Parent چه هستند؟
4. کدام Class را ویرایش می‌کنم؟
5. مقدار Literal است یا باید Variable باشد؟
6. این تغییر در Breakpointهای دیگر چه اثری دارد؟

---

## مدل ذهنی نهایی فصل

هر بار که وارد Editor می‌شوی، این زنجیره را در ذهن مرور کن:

```text
محتوا چه معنایی دارد؟
↓
درخت درست آن چیست؟
↓
کدام Parent مسئول چیدمان است؟
↓
Flex، Grid یا Flow عادی؟
↓
اندازه و فاصله چگونه مذاکره می‌شوند؟
↓
این تصمیم Local است، Global است، Variable است یا Component؟
↓
در Stateها و Breakpointها چه تغییری می‌کند؟
↓
در DevTools واقعاً چه CSSای تولید شده است؟
```

در V3 بیشتر وسوسه می‌شوی هر Widget را جداگانه تنظیم کنی. در V4 باید بیشتر به «سیستم» فکر کنی: Element اتمیک، Parent، Class، Variable، Component و منبع Style. این مقایسه مطلق نیست—V3 نیز Container و Global Setting دارد و V3/V4 می‌توانند کنار هم باشند—اما برای تغییر عادت ذهنی مفید است.

## بزرگ‌ترین اشتباه مبتدی‌ها

مبتدی نتیجهٔ بصری را می‌بیند و مستقیم سراغ Style می‌رود.

مثلاً برای کنار هم بردن دو عنصر:

```text
Margin-left: 180px
```

اما مسئلهٔ واقعی شاید این باشد که Parent باید Flex Row و `justify-content: space-between` باشد.

Style نمی‌تواند ساختار اشتباه را سالم کند؛ فقط آن را پنهان می‌کند.

---

## روش تشخیص سریع

وقتی چیزی درست نیست، این ترتیب را بررسی کن:

```text
Tree → Parent → Display → Size → Spacing → Position → Style → State
```

نه برعکس.

# ۲. درک عمیق Element Tree و انتخاب ظرف درست

## مسئله‌ای که این مفهوم حل می‌کند

بسیاری از خطاهای Layout در واقع خطای CSS نیستند. عناصر در Parent نامناسب قرار گرفته‌اند.

فرض کن عنوان و دکمه باید با هم در سمت راست کارت حرکت کنند، اما هرکدام در Wrapper جدا و دور از هم هستند. هرچقدر Margin و Position بدهی، رابطهٔ واقعی آن‌ها اصلاح نشده است.

---

## تشبیه به دنیای واقعی: پوشه‌های کامپیوتر

Element Tree را مثل ساختار پوشه‌ها تصور کن:

```text
Project
├── Images
│   ├── hero.jpg
│   └── logo.svg
└── Documents
    ├── proposal.pdf
    └── invoice.pdf
```

اگر فایل‌های مربوط به یک موضوع در پوشه‌های پراکنده باشند، مدیریتشان سخت می‌شود.

در Tree:

- **Parent** = پوشه
- **Child** = چیزی که مستقیم داخل پوشه است
- **Sibling** = دو مورد هم‌سطح با Parent مشترک
- **Descendant** = هر چیزی در عمق زیرشاخه
- **Ancestor** = هر Parent در مسیر بالاتر

---

## چرا Tree وجود دارد؟

مرورگر برای Layout، inheritance، انتخابگرهای CSS، دسترسی‌پذیری و رویدادها باید بداند چه چیزی داخل چه چیزی است.

ساختار فقط برای مرتب‌بودن پنل Navigator نیست؛ رفتار صفحه از آن ساخته می‌شود.

---

## سه نوع ظرف را با یک ساختمان مقایسه کن

### Div Block: اتاق خالی

Div یک ظرف عمومی و سبک است. خودش الزاماً موتور پیچیدهٔ توزیع ندارد.

کاربرد:

- گروه‌بندی معنایی یا بصری
- ساخت Shell
- ایجاد مرجع Position
- اعمال Background، Border یا Padding مشترک

### Flex Container: راهروی یک‌محوره

Flex برای توزیع Childها در یک محور اصلی طراحی شده است:

```text
Row:    A → B → C
Column: A
        ↓
        B
        ↓
        C
```

### Grid Container: نقشهٔ خانه با ردیف و ستون

Grid وقتی مفید است که جای‌گذاری هم‌زمان در دو بُعد مهم باشد:

```text
┌───────┬───────┐
│   A   │   B   │
├───────┼───────┤
│   C   │   D   │
└───────┴───────┘
```

---

## اصل «کمترین موتور لازم»

قرار نیست همه‌چیز Flex یا Grid باشد.

از خودت بپرس:

- فقط گروه‌بندی می‌خواهم؟ → Div
- توزیع روی یک محور می‌خواهم؟ → Flex
- رابطهٔ ردیف و ستون می‌خواهم؟ → Grid

موتور قوی‌تر همیشه انتخاب بهتر نیست. موتور اضافی کنترل‌های بیشتر، CSS بیشتر و پیچیدگی ذهنی بیشتر می‌آورد.

---

## مثال واقعی در Elementor

یک کارت محصول:

```text
Product Card
├── Media
│   ├── Image
│   └── Badge
└── Content
    ├── Title
    ├── Price Row
    │   ├── Current Price
    │   └── Old Price
    └── Button
```

تصمیم‌ها:

- Product Card: Div یا Flex Column
- Media: Div با `position: relative`
- Badge: فرزند absolute داخل Media
- Price Row: Flex Row
- Content: Flex Column با Gap

اگر Badge مستقیم داخل Product Card باشد، مرجع Position بزرگ‌تر و مبهم‌تر می‌شود.

---

## رفتار قدم‌به‌قدم

1. تمام نقش‌ها را قبل از ساخت نام‌گذاری کن.
2. مواردی را که باید با هم حرکت، مخفی یا Style شوند زیر Parent مشترک بگذار.
3. فقط Childهای مستقیم Parent از Layout همان Parent فرمان می‌گیرند.
4. اگر یک Wrapper هیچ مسئولیتی ندارد، احتمالاً قابل حذف است.
5. اگر یک Wrapper چند مسئولیت نامرتبط دارد، احتمالاً باید شکسته شود.

---

## تله‌های رایج

### تلهٔ ۱: Wrapper برای هر Element

هر Heading نیاز به Div جدا ندارد. Wrapper باید مسئولیت داشته باشد.

### تلهٔ ۲: Parent بسیار بزرگ

اگر کل Section را Flex Row کنی اما فقط دو Child کوچک باید کنار هم باشند، کنترل Layout بیش از حد گسترده می‌شود.

### تلهٔ ۳: استفاده از Absolute برای جایگزینی Tree

Absolute برای Overlay است، نه برای ساختن Layout اصلی صفحه.

### تلهٔ ۴: اشتباه‌گرفتن Child با Descendant

Flex فقط Child مستقیم را Flex Item می‌کند؛ نوه‌ها توسط Flex Parent بالاتر مستقیماً چیده نمی‌شوند.

---

## روش تشخیص سریع

از هر Wrapper بپرس:

> اگر این Wrapper را حذف کنم، کدام مسئولیت واقعی از بین می‌رود؟

اگر پاسخ «هیچ‌چیز» است، Wrapper احتمالاً اضافی است.

---

## تصویر ذهنی نهایی

Element Tree مثل ساختار پوشه‌هاست. اگر فایل‌ها در پوشهٔ اشتباه باشند، نام‌گذاری زیبا مشکل رابطه را حل نمی‌کند. هر Parent باید دقیقاً همان گروهی را مدیریت کند که یک قانون مشترک دارند.

## قوانین طلایی

- **«Tree نقشهٔ قدرت است؛ Parent تعیین می‌کند Childها چگونه رفتار کنند.»**
- **«Siblingها فقط وقتی با یک قانون مشترک چیده می‌شوند که Parent مشترک معنادار داشته باشند.»**
- **«Div برای گروه‌بندی، Flex برای یک محور، Grid برای دو محور.»**
- **«کمترین موتور لازم، بهترین نقطهٔ شروع است.»**
- **«Wrapper بدون مسئولیت، بدهی ساختاری است.»**

# ۳. درک عمیق Local Class، Global Class و هدف واقعی ویرایش

## مسئله‌ای که این مفهوم حل می‌کند

در V4 ممکن است رنگ یک Heading را تغییر دهی و ناگهان چند Heading دیگر نیز تغییر کنند. یا یک Global Class را ویرایش کنی اما روی Element موردنظر هیچ تغییری نبینی.

علت معمول این است که نمی‌دانی:

- الان کدام Class فعال است؛
- تغییر تو Local است یا Global؛
- کدام Class در تعارض اولویت دارد.

---

## تشبیه به دنیای واقعی: لباس شخصی و یونیفرم

- **Global Class** مثل یونیفرم شرکت است.
- **Local Class** مثل تغییر اختصاصی خیاط روی لباس یک کارمند است.
- **Variable** مثل کد رنگ پارچه است که هم یونیفرم و هم لباس اختصاصی می‌توانند از آن استفاده کنند.

اگر شرکت رنگ یونیفرم را تغییر دهد، همهٔ لباس‌های وابسته تغییر می‌کنند؛ مگر اینکه خیاط روی لباس یک نفر رنگ دیگری دوخته باشد.

---

## تعریف دقیق

### Local Class

هر Element در V4 حداقل یک Local Class دارد. این Class مخصوص همان Element است و طبق مستندات رسمی Elementor بالاترین اولویت را در تعارض‌های Class دارد.

### Global Class

یک بستهٔ Style نام‌دار است که می‌توان آن را روی چند Element اعمال کرد.

مثلاً:

```text
.button-base
.button-primary
.button-large
```

هر Class یک مسئولیت روشن دارد.

---

## چرا Class ساخته شده است؟

بدون Class، هر Element نسخهٔ جداگانه‌ای از تنظیمات را حمل می‌کند:

```text
Button 1: background #6D5DFB, radius 12, padding 16
Button 2: background #6D5DFB, radius 12, padding 16
Button 3: background #6D5DFB, radius 12, padding 16
```

سه ظاهر شبیه داریم، اما رابطه‌ای میان آن‌ها نیست.

با Class:

```text
.button-primary
```

هر سه Button از یک قانون مشترک پیروی می‌کنند.

---

## هدف واقعی ویرایش را قبل از لمس کنترل مشخص کن

از خودت بپرس:

### آیا این تغییر فقط برای همین Element است؟

Local Class.

### آیا این یک الگوی تکرارشونده است؟

Global Class.

### آیا فقط مقدار مشترک است؟

Variable.

### آیا ساختار چندElementی تکرار می‌شود؟

Component.

---

## مثال واقعی

سه دکمه داری:

```text
دکمهٔ اصلی: خرید
دکمهٔ اصلی: ثبت‌نام
دکمهٔ ثانویه: اطلاعات بیشتر
```

سیستم مناسب:

```text
.button-base       ← Typography، Padding، Radius
.button-primary    ← رنگ اصلی
.button-secondary  ← Border و Background ثانویه
```

روی دکمهٔ خرید:

```text
Local Class
+ button-base
+ button-primary
```

اگر فقط دکمهٔ خرید نیاز به عرض کامل در Hero دارد، Width را در Local Class یا یک Utility Class معنادار قرار بده؛ نه اینکه `button-primary` را برای همه خراب کنی.

---

## تعارض چگونه رخ می‌دهد؟

فرض کن:

```text
.text-red   → color: red
.text-green → color: green
```

هر دو روی یک Paragraph هستند.

Elementor باید تصمیم بگیرد کدام برنده است. ترتیب Global Classها در Class Manager برای این اولویت اهمیت دارد، اما Local Class بالاتر از Global Classها قرار می‌گیرد.

پس اگر Global Class را عوض کردی و نتیجه دیده نشد، اول Local Class را بررسی کن.

---

## در Elementor V4

قبل از هر Style:

1. Classes Field را ببین.
2. Class فعال را تشخیص بده.
3. مطمئن شو State درست را ویرایش می‌کنی.
4. اگر Global Class است، دامنهٔ مصرف آن را در ذهن داشته باش.
5. تغییر را روی چند مصرف‌کننده آزمایش کن.

---

## Utility Class؛ ابزار کوچک، مسئولیت کوچک

گاهی یک رفتار کوچک در ده‌ها نقطه تکرار می‌شود، اما ساخت Component برای آن زیاده‌روی است. اینجا می‌توان از یک Global Class کمکی استفاده کرد:

```text
u-flex-center
u-full-width
u-overflow-hidden
u-space-block-end-lg
```

Utility Class را مثل آچار کوچکی تصور کن که فقط یک کار روشن انجام می‌دهد. اگر یک Class هم‌زمان رنگ، Typography، Layout و Responsive را کنترل کند، دیگر Utility نیست؛ تبدیل به بسته‌ای مبهم شده است.

برای سایت فارسی، Utilityها را تا جای ممکن با Logical Propertyها طراحی کن. `padding-inline` از `padding-left` و `padding-right` قابل‌حمل‌تر است، چون با RTL و LTR سازگار می‌ماند. Utility Class یک «نوع رسمی جداگانه» در Elementor نیست؛ یک الگوی معماری است که با Global Class پیاده می‌شود.

## درخت ردیابی منبع Style

وقتی یک Style اعمال نمی‌شود، فقط به Specificity فکر نکن. در V4 ابتدا این زنجیره را بررسی کن:

```text
Breakpoint فعال
↓
State فعال
↓
Class انتخاب‌شده برای ویرایش
↓
Local Class
↓
Global Classهای رقیب و ترتیب Class Manager
↓
Custom CSS
↓
Cascade واقعی مرورگر و Computed Style
```

Local Class در قرارداد Elementor بالاترین اولویت را دارد. میان Global Classها، کلاسی که در Class Manager اولویت بالاتری دارد برنده می‌شود. سپس Custom CSS، Selector Specificity، Source Order و `!important` نیز ممکن است در خروجی واقعی دخالت کنند. بنابراین «اولویت Elementor» و «Specificity CSS» یک چیز نیستند.


## تله‌های رایج

- ساخت Global Class برای یک استثنای تک‌مصرف
- قرار دادن همهٔ Styleها در Local Class و ازبین‌بردن قابلیت نگهداری
- نام‌گذاری بر اساس ظاهر لحظه‌ای، مثل `.blue-text`، وقتی نقش واقعی `.text-accent` است
- ویرایش Global Class بدون بررسی سایت
- حل تعارض با افزودن Class جدید به‌جای پاک‌کردن Property متعارض

---

## قانون نام‌گذاری

نام خوب می‌گوید Class چه **نقشی** دارد:

```text
خوب: card-title
خوب: button-primary
خوب: stack-sm
ضعیف: text-18-blue
ضعیف: box2-final-new
```

---

## تصویر ذهنی نهایی

Local Class لباس سفارشی یک نفر است؛ Global Class یونیفرم یک گروه؛ Utility Class ابزار کوچکی مثل کمربند یا کلاه؛ Variable رنگ و اندازه‌ای است که از انبار مرکزی می‌آید. پیش از ویرایش، مشخص کن دستت روی کدام لایه است.

## قوانین طلایی

- **«Local Class استثنای همان Element است؛ Global Class قرارداد مشترک چند Element.»**
- **«قبل از ویرایش Style، اول Class فعال را بخوان.»**
- **«اگر Global Class دیده نمی‌شود، Local Class را به‌عنوان مظنون اول بررسی کن.»**
- **«Class باید نقش را نام‌گذاری کند، نه تصادف ظاهری امروز را.»**
- **«تکرار اثبات‌شده را Global کن؛ حدس دربارهٔ تکرار آینده را نه.»**

- Elementor Help: Prioritize conflicting styles
- Elementor Help: The Elementor Editor Class Manager
- CSS Cascade specification

# ۴. درک عمیق Box Model، Width، Padding و Margin

## تصویر ذهنی اصلی: خانه و حیاط

هر Element را مثل یک خانه تصور کن:

```text
┌──────────────────────────┐
│          Margin          │  ← حیاط بیرونی
│   ┌──────────────────┐   │
│   │      Border      │   │  ← دیوار
│   │  ┌────────────┐  │   │
│   │  │  Padding   │  │   │  ← فضای داخل
│   │  │ ┌────────┐ │  │   │
│   │  │ │Content │ │  │   │  ← وسایل خانه
│   │  │ └────────┘ │  │   │
│   │  └────────────┘  │   │
│   └──────────────────┘   │
└──────────────────────────┘
```

تعریف «Padding داخل است و Margin بیرون» درست است، اما برای فهم Width و Overflow کافی نیست.

---

## چهار لایهٔ Box

1. **Content Box:** متن، تصویر یا محتوای اصلی
2. **Padding Box:** فضای تنفس بین محتوا و Border
3. **Border Box:** لبهٔ قابل‌دیدن جعبه
4. **Margin Box:** فضای بیرونی برای رابطه با همسایه‌ها

---

## Padding؛ فضای داخل ملک

Padding خود Element را بزرگ‌تر می‌کند و Background وارد آن می‌شود.

```css
.card {
  background: #fff;
  padding: 24px;
}
```

Background سفید هم پشت محتوا و هم پشت Padding دیده می‌شود.

### چرا ساخته شده؟

برای اینکه محتوا به دیوارهٔ خودش نچسبد.

### در Elementor

Padding روی Container یا Element یعنی محتوا از لبه‌های همان جعبه فاصله می‌گیرد.

> **قانون:** Padding دیوار را از وسایل داخل خانه دور می‌کند.

---

## Margin؛ فضای بیرون ملک

Margin بین Border یک Element و محیط اطراف آن فاصله ایجاد می‌کند. Background وارد Margin نمی‌شود.

```css
.card {
  margin-block-end: 32px;
}
```

### چرا ساخته شده؟

برای رابطهٔ بیرونی جعبه با همسایه‌ها.

> **قانون:** Margin خانه را از همسایه‌ها دور می‌کند.

---

## Width واقعاً چه چیزی را اندازه می‌گیرد؟

پاسخ به `box-sizing` بستگی دارد.

### حالت پیش‌فرض: content-box

```css
.box {
  width: 300px;
  padding: 20px;
  border: 2px solid;
}
```

عرض مرزی واقعی:

```text
300 + 20 + 20 + 2 + 2 = 344px
```

### حالت رایج: border-box

```css
.box {
  box-sizing: border-box;
  width: 300px;
  padding: 20px;
  border: 2px solid;
}
```

در این حالت Padding و Border داخل همان 300px محاسبه می‌شوند.

---

## Width، Min-width و Max-width

این سه را یک قرارداد ببین:

- `width` = اندازهٔ ترجیحی یا اعلام‌شده
- `min-width` = از این کوچک‌تر نشو
- `max-width` = از این بزرگ‌تر نشو

مثال استاندارد Shell:

```css
.shell {
  width: min(100% - 32px, 1200px);
  margin-inline: auto;
}
```

در Elementor می‌توان همان منطق را با Width، Max Width و Padding کناری ساخت.

---

## چرا `width: 100%` گاهی Overflow می‌دهد؟

در `content-box`، 100٪ فقط Content را می‌گیرد و Padding/Border ممکن است به آن اضافه شوند.

همچنین اگر به Element تمام‌عرض Margin افقی مثبت بدهی، Outer Size از Parent بزرگ‌تر می‌شود.

```text
Parent = 1000px
Child width = 1000px
Margin left + right = 40px
Outer width = 1040px
```

---

## Margin Collapse؛ نکته‌ای که باید دقیق بدانی

Marginهای عمودی بعضی Blockها در Normal Flow ممکن است با هم Collapse شوند؛ یعنی جمع ساده نشوند و به یک Margin مشترک تبدیل شوند.

اما این رفتار در Flex و Grid Itemها مانند Normal Block Flow رخ نمی‌دهد.

پس اگر دو Margin عمودی نتیجهٔ عجیب دارند، ابتدا نوع Layout را بررسی کن.

---

## پل به DevTools؛ خانه را واقعاً ببین

در مرورگر روی Element راست‌کلیک کن و **Inspect** را بزن. در پنل **Computed** یا نمای Box Model می‌توانی چهار لایهٔ Content، Padding، Border و Margin را با اندازهٔ واقعی ببینی. اینجا تفاوت عددی `content-box` و `border-box` دیگر یک تعریف حفظی نیست؛ مرورگر عرض نهایی را جلوی چشمت نشان می‌دهد.

برای عیب‌یابی Overflow، فقط عدد Width را نگاه نکن. Min Width، Padding، Border، Scrollbar، Gap و محتوای نشکن را هم در Computed Style بررسی کن.

## سناریوی واقعی Elementor

یک کارت خدمات:

```text
Card
├── Icon
├── Heading
└── Description
```

- فضای محتوا از لبهٔ کارت → Padding کارت
- فاصلهٔ Icon و Heading → Gap Parent یا Margin منطقی
- فاصلهٔ کارت با کارت بعد → Gap Grid/Flex یا Margin بیرونی
- محدودکردن پهنای کارت → Width/Max Width

---

## تله‌های رایج

- استفاده از Margin برای فاصلهٔ محتوای داخل کارت
- افزودن `overflow: hidden` بدون پیدا کردن علت Overflow
- دادن Width ثابت به محتوای Responsive
- فراموش‌کردن Border و Padding در محاسبهٔ اندازه
- استفاده از Marginهای پراکنده به‌جای Gap در Siblingهای تکراری

---

## روش تشخیص سریع

بپرس:

### چه چیزی باید فاصله بگیرد؟

- محتوا از لبهٔ خودش → Padding
- خود Element از همسایه → Margin یا Gap
- چند Sibling با فاصلهٔ یکنواخت → Gap

### چه چیزی از Parent بیرون زده؟

DevTools را باز کن و Content/Padding/Border/Margin را جدا ببین.

---

## تصویر ذهنی نهایی

Content وسایل خانه، Padding فضای حرکت داخل، Border دیوار و Margin حیاط بیرون است. `border-box` می‌گوید عدد عرض، دیوار تا دیوار را شامل شود؛ `content-box` عدد را فقط برای فضای وسایل نگه می‌دارد.

## قوانین طلایی

- **«Padding فضای داخل ملک است؛ Margin فضای بیرون ملک.»**
- **«Background وارد Padding می‌شود، وارد Margin نمی‌شود.»**
- **«Width بدون دانستن `box-sizing` عدد کاملی نیست.»**
- **«اگر چند Sibling فاصلهٔ مشترک دارند، Gap معمولاً از Margin تمیزتر است.»**
- **«Overflow را پنهان نکن؛ منبع اندازهٔ اضافه را پیدا کن.»**
- **«`min-width` و محتوای نشکن می‌توانند از Width قوی‌تر ظاهر شوند.»**

### منابع رسمی این فصل

- MDN: CSS Box Model
- MDN: box-sizing
- Elementor Help: Style tab — Size
- Elementor Help: Style tab — Spacing

# ۵. درک عمیق Flexbox؛ چیدمان یک‌بعدی و رابطهٔ Parent/Item

## مسئله‌ای که Flexbox حل می‌کند

قبل از Flexbox، کنار هم گذاشتن، وسط‌چین‌کردن و توزیع منعطف Elementها اغلب به Float، Inline-block یا ترفندهای پیچیده نیاز داشت.

Flexbox برای یک سؤال ساخته شد:

> چگونه چند Item را در یک محور بچینیم و فضای اضافه یا کمبود را میان آن‌ها مدیریت کنیم؟

---

## تشبیه به دنیای واقعی: واگن و چمدان‌ها

- Flex Container = واگن
- Flex Item = چمدان مستقیم داخل واگن
- Main Axis = مسیر طولی واگن
- Cross Axis = عرض واگن
- Basis = اندازهٔ اولیهٔ هر چمدان
- Grow = سهم هر چمدان از فضای اضافه
- Shrink = سهم هر چمدان از کمبود فضا
- Gap = فاصلهٔ ثابت میان چمدان‌ها

نوه‌ای که داخل یکی از چمدان‌هاست، مستقیماً با قانون واگن چیده نمی‌شود.

---

## تعریف دقیق

Flexbox یک مدل Layout **یک‌بعدی** است. یک‌بعدی یعنی تصمیم اصلی حول یک محور انجام می‌شود؛ Row یا Column.

این به معنی ناتوانی در کنترل محور دیگر نیست. Align روی محور متقاطع عمل می‌کند، اما منطق اصلی توزیع اندازه و ترتیب در Main Axis است.

---

## Parent چه چیزی را کنترل می‌کند؟

Flex Container معمولاً این رفتارها را تعیین می‌کند:

- Direction
- Wrap
- Justify Content
- Align Items
- Align Content در حالت چندخطی
- Gap

## Item چه چیزی را کنترل می‌کند؟

Flex Item معمولاً این موارد را حمل می‌کند:

- Basis
- Grow
- Shrink
- Order
- Align Self
- Min/Max Size

---

## مثال ساده

```css
.parent {
  display: flex;
  flex-direction: row;
  gap: 24px;
}
```

فقط Childهای مستقیم `.parent` Flex Item می‌شوند.

```text
Parent
├── A  ← Flex Item
├── B  ← Flex Item
└── C  ← Flex Item
    └── D  ← Flex Item این Parent نیست
```

---

## چرا Flex را «مذاکرهٔ اندازه» می‌نامیم؟

Itemها فقط Width ثابت ندارند. مرورگر این اطلاعات را کنار هم می‌گذارد:

1. اندازهٔ اولیه یا Basis
2. محتوای داخلی
3. Min/Max constraints
4. فضای موجود Parent
5. Grow یا Shrink
6. Gapها

سپس Used Size را محاسبه می‌کند.

---

## سناریوی Elementor: Hero دو ستونه

```text
Hero Flexbox — Row
├── Copy — basis 55%
└── Visual — basis 45%
```

روی موبایل:

```text
Hero Flexbox — Column
├── Copy
└── Visual
```

در این مدل، تغییر Direction ساختار را Responsive می‌کند؛ نیازی نیست نسخهٔ دوم Section بسازی و یکی را مخفی کنی.

---

## ترتیب صحیح تنظیم Flex

1. Parent مناسب را انتخاب کن.
2. Direction را مشخص کن.
3. اندازهٔ اولیهٔ Itemها را بررسی کن.
4. فضای آزاد یا کمبود را تشخیص بده.
5. Grow/Shrink را تنظیم کن.
6. Justify/Align را اعمال کن.
7. Gap و Wrap را تنظیم کن.
8. در عرض‌های واقعی تست کن.

اگر از مرحلهٔ ۶ شروع کنی، ممکن است Alignment کار نکند چون فضای آزادی وجود ندارد.

---

## تله‌های رایج

- تصور اینکه Flex همیشه دو ستون مساوی می‌سازد
- استفاده از Justify برای حل Width اشتباه
- فراموش‌کردن `min-width: auto` و محتوای بلند
- دادن Flex به Parent اشتباه
- استفاده از Order برای تغییر معنای محتوا بدون بررسی ترتیب Keyboard/DOM
- استفاده از Flex برای Layout واقعاً دوبعدی و پیچیده

---

## Flex یا Grid؟

از خودت بپرس:

- آیا بیشتر دربارهٔ «توالی در یک خط/ستون» فکر می‌کنم؟ → Flex
- آیا دربارهٔ «مختصات ردیف و ستون» فکر می‌کنم؟ → Grid

---

## پل به DevTools

Badge مربوط به `flex` را کنار Parent فعال کن. سپس در Computed Style، `display`، `flex-direction`، `gap` و اندازهٔ Childها را ببین. اگر یک Child برخلاف انتظار رفتار می‌کند، ابتدا ثابت کن Flex Item مستقیم همین Parent است؛ نوه‌ها از Flex Parent بالاتر مستقیماً فرمان نمی‌گیرند.

## تصویر ذهنی نهایی

Flex Container واگنی است که قانون حرکت را تعیین می‌کند و Childهای مستقیم چمدان‌هایی هستند که درباره سهم فضا مذاکره می‌کنند. چمدان داخل چمدان از قانون واگن بیرونی مستقیماً فرمان نمی‌گیرد.

## قوانین طلایی

- **«Flex Parent فضا را مدیریت می‌کند؛ Flex Item برای سهم خود مذاکره می‌کند.»**
- **«فقط Child مستقیم Flex Item است.»**
- **«Direction محور اصلی را می‌سازد؛ بقیهٔ کنترل‌ها نسبت به آن معنا می‌گیرند.»**
- **«Alignment جای Size را نمی‌گیرد.»**
- **«Flex برای توالی یک‌بعدی است؛ Grid برای نقشهٔ دوبعدی.»**

# ۶. درک عمیق Direction، Justify، Align و Gap

## بزرگ‌ترین اشتباه حفظی

بعضی‌ها می‌گویند:

```text
Justify = افقی
Align = عمودی
```

این فقط در `flex-direction: row` غالباً درست به نظر می‌رسد. با Column همه‌چیز عوض می‌شود.

---

## تشبیه: ریل قطار و سکوی ایستگاه

- Direction = جهت ریل
- Main Axis = طول ریل
- Cross Axis = عرض سکو
- Justify = توزیع قطارها در طول ریل
- Align = قرارگیری قطارها در عرض سکو
- Gap = فاصلهٔ ثابت میان قطارها

---

## Direction محور را تعریف می‌کند

### Row

```text
Main Axis:  شروع → پایان
Cross Axis: بالا ↓ پایین
```

### Column

```text
Main Axis:  بالا ↓ پایین
Cross Axis: شروع → پایان
```

در RTL، Start و End افقی ممکن است نسبت به LTR جابه‌جا شوند. به همین دلیل بهتر است محور را مفهومی بخوانی، نه صرفاً چپ و راست.

---

## تصویر محور چرخان

```text
Row                         Column
Main  ─────────────→        Cross ─────────────→
Cross ↓                     Main  ↓
```

با تغییر Direction، تعریف Justify و Align عوض نمی‌شود؛ خودِ محور می‌چرخد. `justify-content` همیشه روی Main Axis است و `align-items` همیشه روی Cross Axis. در `row-reverse` و `column-reverse` محور عوض نمی‌شود؛ فقط جهت Start و End همان محور برعکس می‌شود.

در Chrome DevTools، Badge مربوط به `flex` را کنار Container فعال کن تا محور، فاصله و جای Childها را به‌صورت Overlay ببینی.

## Justify Content

Justify فضای آزاد روی Main Axis را توزیع می‌کند.

نمونه‌ها:

```text
flex-start:    [A][B][C].........
center:        ....[A][B][C].....
space-between: [A].....[B].....[C]
```

### نکتهٔ حیاتی

اگر فضای آزاد وجود نداشته باشد، Justify چیزی برای توزیع ندارد.

مثلاً اگر Itemها با Grow تمام عرض را مصرف کرده‌اند، `space-between` ممکن است اثر مورد انتظار را نشان ندهد.

---

## Align Items

Align Items جای Itemها را روی Cross Axis کنترل می‌کند.

در Row:

- Cross Axis معمولاً عمودی است.

در Column:

- Cross Axis معمولاً افقی است.

`stretch` می‌تواند Itemها را در Cross Axis کش دهد، به‌شرط اینکه اندازهٔ صریح مانع آن نشود.

---

## Align Self

اگر فقط یک Item باید متفاوت باشد، Align Self روی همان Item اعمال می‌شود.

مثل دانش‌آموزی که در یک صف، جای خاص خود را دارد.

---

## Gap

Gap فاصلهٔ بین Itemها یا Lineهاست و به خود Item خاصی تعلق ندارد.

```css
.stack {
  display: flex;
  flex-direction: column;
  gap: 16px;
}
```

مزیت Gap نسبت به Margin:

- روی ابتدا و انتهای گروه فاصلهٔ اضافه ایجاد نمی‌کند.
- با حذف یا اضافه‌شدن Item منطق تمیزتری دارد.
- رابطهٔ Parent با Siblingها را بیان می‌کند.

---

## مثال Elementor: نوار دکمه‌ها

```text
Actions — Flex Row
├── Primary Button
└── Secondary Button
```

تنظیم:

```text
Direction: Row
Justify: Start
Align: Center
Gap: 12px
```

روی Mobile:

```text
Direction: Column
Align: Stretch
```

بدون تغییر HTML، دکمه‌ها زیر هم و تمام‌عرض می‌شوند.

---

## روش عیب‌یابی چهارمرحله‌ای

1. Direction چیست؟
2. Main Axis کدام است؟
3. آیا فضای آزاد وجود دارد؟
4. می‌خواهم روی Main Axis تغییر دهم یا Cross Axis؟

پس از پاسخ، Justify یا Align را انتخاب کن.

---

## تله‌های رایج

- حفظ‌کردن افقی/عمودی به‌جای Main/Cross
- استفاده از Margin برای فاصلهٔ یکنواخت Siblingها
- انتظار اثر از Justify بدون فضای آزاد
- انتظار Stretch وقتی Item Width/Height صریح دارد
- اشتباه‌گرفتن Align Items با Align Content

---

## Align Content چه زمانی مهم می‌شود؟

وقتی Flex چند Line دارد و Container در Cross Axis فضای اضافه دارد. Align Content خود Lineها را توزیع می‌کند؛ Align Items، Itemهای داخل هر Line را.

---

## تصویر ذهنی نهایی

Direction ریل را می‌چرخاند. Justify قطارها را روی طول ریل جابه‌جا می‌کند و Align جای آن‌ها را روی عرض سکو تعیین می‌کند. تعریف‌ها ثابت‌اند؛ این محور است که می‌چرخد.

## قوانین طلایی

- **«Direction را بخوان؛ بعد دربارهٔ Justify و Align تصمیم بگیر.»**
- **«Justify همیشه روی Main Axis است، نه همیشه افقی.»**
- **«Align Items همیشه روی Cross Axis است، نه همیشه عمودی.»**
- **«بدون فضای آزاد، توزیع فضای آزاد معنی ندارد.»**
- **«Gap رابطهٔ میان Siblingهاست؛ Margin ویژگی بیرونی یک Box.»**

### منابع رسمی این فصل

- CSS Box Alignment Module
- CSS Flexbox specification
- MDN: Box alignment in flexbox
- Elementor Help: Container layout and arrangement controls

# ۷. درک عمیق Flex Basis، Grow و Shrink

## مسئله‌ای که این مفهوم حل می‌کند

دو ستون ممکن است هر دو 50٪ دیده شوند، اما رفتارشان در عرض کم کاملاً متفاوت باشد.

یکی با Width ساخته شده، دیگری با Basis و Grow. ظاهر Desktop یکسان است، اما قرارداد Responsive آن‌ها یکسان نیست.

---

## تشبیه: تقسیم میز غذا

سه نفر دور یک میز نشسته‌اند:

- Basis = سهم اولیهٔ هر نفر
- Grow = سهم از غذای اضافه
- Shrink = سهم از کمبود جا
- Min/Max = محدودیت رژیم یا ظرفیت بشقاب

مرورگر ابتدا سهم اولیه را می‌بیند، سپس فضای اضافه یا کمبود را تقسیم می‌کند.

---

## Flex Basis

`flex-basis` اندازهٔ آغازین Flex Item روی Main Axis است.

- در Row معمولاً به عرض اولیه مربوط می‌شود.
- در Column معمولاً به ارتفاع اولیه مربوط می‌شود.

`auto` یعنی مرورگر از اندازهٔ اصلی، Width/Height و محتوا برای تعیین Basis کمک می‌گیرد.

---

## Flex Grow

Grow فقط **فضای مثبت باقی‌مانده** را تقسیم می‌کند.

مثال:

```text
Container = 1000px
Basis A = 200px
Basis B = 200px
Gap = 20px
فضای باقی‌مانده = 580px
```

اگر:

```text
A grow = 1
B grow = 1
```

هرکدام نیمی از 580px اضافه را می‌گیرند.

اگر:

```text
A grow = 2
B grow = 1
```

فضای اضافه با نسبت 2 به 1 تقسیم می‌شود؛ نه اینکه اندازهٔ نهایی الزاماً دقیقاً 2 برابر شود.

---

## Flex Shrink

Shrink وقتی فعال می‌شود که مجموع اندازه‌های اولیه، Gap و محدودیت‌ها از Parent بزرگ‌تر باشد.

Shrink مشخص می‌کند هر Item چقدر در حذف فضای منفی مشارکت کند.

اما محاسبه فقط نسبت ساده نیست؛ اندازهٔ پایه و Min Size نیز اثر دارند.

---

## تلهٔ مشهور `min-width: auto`

Flex Itemها معمولاً به‌طور پیش‌فرض حاضر نیستند از اندازهٔ حداقلی محتوای خود کوچک‌تر شوند.

یک URL طولانی، متن بدون شکست یا تصویر می‌تواند باعث Overflow شود.

راه‌حل رایج در CSS خام:

```css
.flex-item {
  min-width: 0;
}
```

در Elementor باید Min Width، Overflow و رفتار محتوای Child را بررسی کنی؛ فقط Shrink را زیاد نکن.

---

## مثال Elementor: متن و تصویر

```text
Hero
├── Copy: basis 60%, grow 1, shrink 1
└── Image: basis 40%, grow 0, shrink 1
```

این قرارداد می‌گوید:

- Copy سهم اولیهٔ بیشتری دارد.
- Copy می‌تواند فضای اضافه را بگیرد.
- هر دو در کمبود جا می‌توانند کوچک شوند.

اما اگر تصویر `min-width: 500px` داشته باشد، Shrink ممکن است نتواند Layout را نجات دهد.

---

## مهندسی معکوس Flex در پنل V4

دانستن `flex: 1 1 0` کافی نیست؛ باید بفهمی کنترل‌های V4 چه CSSای تولید کرده‌اند. این سه مقدار در CSS یعنی:

```css
flex-grow: 1;
flex-shrink: 1;
flex-basis: 0;
```

اما خالی‌گذاشتن Width در رابط لزوماً به معنای `flex-basis: 0` نیست؛ ممکن است Basis مؤثر `auto` باشد و اندازهٔ محتوا وارد مذاکره شود. پس جدول زیر «ترجمه نیت» است، نه وعدهٔ خروجی ثابت:

| نیت طراحی | تنظیم اولیه در V4 | چیزی که در DevTools باید تأیید شود |
|---|---|---|
| دو ستون منعطف بر اساس محتوا | Width بدون مقدار صریح، Grow برابر، Shrink فعال | `flex-basis` مؤثر و Min Size |
| دو سهم واقعاً مساوی از پایه صفر | کنترل‌هایی که Basis صفر تولید کنند | `flex: 1 1 0` یا معادل آن |
| سایدبار ثابت و محتوای شناور | Sidebar: Width 300px، Grow 0، Shrink 0؛ Content: Grow 1، Shrink 1 | ثابت‌ماندن Sidebar و `min-width: 0` روی Content در صورت نیاز |

در Flex Row، `width: 100%` روی تمام Childها معمولاً با هدف چندستونه تعارض دارد؛ چون هر Child می‌خواهد عرض کامل Parent را مبنا بگیرد. اما این مقدار «همیشه سم» نیست: در Flex Column یا زمانی که عمداً هر Item باید یک ردیف کامل بگیرد، می‌تواند درست باشد.

### قانون عملی

> در Flex Row، وقتی Grow قرار است فضا را تقسیم کند، Width را بی‌دلیل روی 100٪ قفل نکن. ابتدا Basis، Grow، Shrink و Min Size را به‌عنوان یک قرارداد واحد ببین.

## Width یا Basis؟

در Flex، Basis معمولاً زبان مستقیم‌تری برای سهم اولیه در Main Axis است.

اما Width هنوز مهم است:

- خارج از Flex
- به‌عنوان ورودی `flex-basis: auto`
- برای Min/Max constraints
- برای اندازهٔ خود محتوا یا Child

پس این دو دشمن هم نیستند؛ باید بدانیم کدام مرحله از محاسبه را کنترل می‌کنند.

---

## ترتیب عیب‌یابی

1. Direction چیست؟
2. Main Size Parent چقدر است؟
3. Basis هر Item چیست؟
4. Gapها چقدرند؟
5. فضای مثبت داریم یا منفی؟
6. Grow یا Shrink چه نسبت‌هایی دارند؟
7. Min/Max و محتوای نشکن مانع هستند؟

---

## مثال 50/50 قابل‌اعتماد

```css
.item {
  flex: 1 1 0;
  min-width: 0;
}
```

این الگو فضای موجود را از پایهٔ صفر با Grow مساوی تقسیم می‌کند. اما همیشه بهترین انتخاب نیست؛ محتوای دو ستون ممکن است نیاز واقعی متفاوتی داشته باشد.

---

## تصویر ذهنی نهایی

Basis پیشنهاد اولیه هر مسافر برای جاست؛ Grow تقسیم صندلی‌های خالی و Shrink تقسیم کمبود جاست. Min Size می‌تواند بگوید یک مسافر از اندازه‌ای کوچک‌تر نمی‌شود، حتی اگر بقیه آماده فشرده‌شدن باشند.

## قوانین طلایی

- **«Basis اندازهٔ شروع مذاکره است؛ Grow و Shrink نتیجهٔ مذاکره را تغییر می‌دهند.»**
- **«Grow اندازهٔ نهایی را نسبت‌بندی نمی‌کند؛ فقط فضای اضافه را نسبت‌بندی می‌کند.»**
- **«Shrink بدون بررسی Min Size و محتوای نشکن کامل نیست.»**
- **«ظاهر 50/50 در Desktop، قرارداد Responsive را ثابت نمی‌کند.»**
- **«در Flex ابتدا Basis را بفهم، بعد Width را تفسیر کن.»**

### منابع رسمی این فصل

- MDN: flex-basis
- MDN: flex-grow
- MDN: flex-shrink
- CSS Flexible Box Layout specification
- Elementor Help: Set Flexbox Container size and behavior

# ۸. درک عمیق Wrap؛ وقتی یک ردیف دیگر جا ندارد

## مسئله‌ای که Wrap حل می‌کند

یک Flex Container را تصور کن که شش کارت داخل آن قرار گرفته است. در صفحهٔ بزرگ، همهٔ کارت‌ها کنار هم جا می‌شوند. اما با کم‌شدن عرض، مرورگر باید تصمیم بگیرد:

- کارت‌ها را کوچک کند؛
- آن‌ها را از کادر بیرون بزند؛
- یا بخشی از کارت‌ها را به خط بعد ببرد.

`flex-wrap` فقط به سؤال سوم پاسخ می‌دهد: **آیا Flex Itemها اجازه دارند بیش از یک Flex Line بسازند؟**

Wrap خودش عرض کارت‌ها، تعداد ستون‌ها یا حداقل اندازهٔ آن‌ها را تعیین نمی‌کند. فقط در را برای ساخت خط جدید باز می‌کند.

---

## تشبیه به دنیای واقعی: صندوق‌های فروشگاه

فرض کن فروشگاه فقط یک صف صندوق دارد.

```text
[نفر ۱][نفر ۲][نفر ۳][نفر ۴][نفر ۵]
```

اگر فضا کم شود و قانون `nowrap` باشد، همه مجبورند در همان یک صف بمانند؛ یا به هم فشرده می‌شوند یا صف از سالن بیرون می‌زند.

با Wrap، وقتی صف اول پر شد، صندوق دوم باز می‌شود:

```text
[نفر ۱][نفر ۲][نفر ۳]
[نفر ۴][نفر ۵]
```

اما بازشدن صندوق دوم تعیین نمی‌کند هر نفر چقدر جا بگیرد. اندازهٔ هر Item همچنان از Width، Basis، Min/Max Size و محتوای آن می‌آید.

---

## چرا CSS این مفهوم را ساخته است؟

Flexbox یک مدل یک‌بعدی است. در هر Flex Line، Itemها روی Main Axis مذاکره می‌کنند. گاهی یک Line کافی نیست، اما هنوز می‌خواهیم منطق اصلی «صف» حفظ شود.

Wrap برای همین ساخته شد:

> یک جریان یک‌بعدی را نگه دار، ولی اجازه بده در صورت کمبود فضا خط‌های بیشتری تشکیل شوند.

این با Grid فرق دارد. در Grid، ردیف و ستون از ابتدا بخشی از شبکه‌اند. در Flex Wrap، خط دوم نتیجهٔ کمبود فضاست، نه لزوماً یک ردیف از پیش طراحی‌شده.

---

## رفتار قدم‌به‌قدم

فرض کن Parent عرض مفید ۹۶۰px دارد و سه کارت هرکدام Basis برابر ۳۰۰px دارند، با Gap برابر ۳۰px:

```text
300 + 300 + 300 + 30 + 30 = 960px
```

سه کارت دقیقاً جا می‌شوند.

اگر Parent به ۸۰۰px برسد، چند اتفاق ممکن است بیفتد:

1. اگر Shrink اجازه دهد و Min Size مانع نباشد، کارت‌ها کوچک می‌شوند.
2. اگر Shrink نتواند فضای لازم را پس بگیرد و Wrap خاموش باشد، Overflow رخ می‌دهد.
3. اگر Wrap روشن باشد، یکی از کارت‌ها به خط بعد می‌رود.

پس ترتیب فکرکردن چنین است:

```text
عرض Parent
↓
Basis/Width Itemها
↓
Gap و Padding
↓
Shrink و Min Size
↓
Wrap
↓
Alignment بین Lineها
```

---

## فرق `align-items` و `align-content`

وقتی فقط یک Line وجود دارد، `align-content` تقریباً موضوعی برای کارکردن ندارد.

- `align-items` جای Itemها را داخل هر Line روی Cross Axis کنترل می‌کند.
- `align-content` خودِ Lineها را در فضای اضافهٔ Cross Axis توزیع می‌کند.

تصویر ذهنی:

```text
Container بلند
┌─────────────────────────┐
│ [A] [B] [C]             │ ← Line 1
│                         │
│ [D] [E]                 │ ← Line 2
└─────────────────────────┘
```

`align-items` قد Itemها را در هر خط می‌بیند؛ `align-content` فاصله و جای دو خط را در کل Container می‌بیند.

---

## در Elementor V4

در تنظیمات Layout یک Flex Container، Wrap را فقط بعد از تعیین قرارداد اندازه Childها فعال کن.

سناریوی Logo Strip:

```text
Logo Strip
├── Logo 1
├── Logo 2
├── Logo 3
├── Logo 4
└── Logo 5
```

تنظیم منطقی ممکن است چنین باشد:

```text
Parent: Row + Wrap
Gap: 24px
Logo item: Width/Basis کنترل‌شده
Image: Max Width مشخص
```

اگر فقط Wrap را فعال کنی ولی هر لوگو `width: 100%` داشته باشد، احتمالاً هر لوگو یک خط کامل می‌گیرد. اگر لوگوها Shrink نامحدود داشته باشند، ممکن است آن‌قدر کوچک شوند که هرگز Wrap رخ ندهد.

### تستی که باید انجام دهی

فقط Desktop، Tablet و Mobile را نبین. عرض‌های میان آن‌ها را نیز امتحان کن:

```text
1200 → 1024 → 900 → 768 → 600 → 480 → 360
```

بسیاری از شکست‌های Wrap دقیقاً بین Breakpointهای رسمی دیده می‌شوند.

---

## Wrap یا Grid؟

این درخت تصمیم را به خاطر بسپار:

```text
آیا Itemها یک جریان طبیعی دارند و فقط در کمبود فضا باید به خط بعد بروند؟
└── Flex + Wrap

آیا ستون‌ها باید در چند ردیف دقیقاً با هم تراز بمانند؟
└── Grid

آیا یک Item باید دو یا چند ستون را بگیرد؟
└── Grid

آیا تعداد Itemها متغیر است و ترتیب خطی محتوا مهم است؟
└── Flex + Wrap را ابتدا بررسی کن
```

چیدمان ۴→۲→۱ فقط مخصوص Grid نیست؛ Flex Wrap هم می‌تواند آن را بسازد. تفاوت اصلی در «رابطهٔ دوبعدی» و «تراز Trackها» است.

---

## اشتباهات رایج

### انتظار Wrap در حالی که Childها Shrink می‌شوند

اگر Itemها می‌توانند تا اندازه‌ای بسیار کوچک جمع شوند، مرورگر شاید هرگز مجبور به ساخت خط دوم نشود.

### Height ثابت روی Parent چندخطی

وقتی تعداد Lineها تغییر می‌کند، Height ثابت می‌تواند خط‌های بعدی را Clip کند یا Overflow بسازد.

### تغییر ترتیب بصری

استفاده از `order` یا Wrap معکوس ممکن است ترتیب دیداری را از ترتیب DOM جدا کند. کاربر کیبورد و Screen Reader همچنان ترتیب DOM را دنبال می‌کند.

### ساخت نسخهٔ جداگانه Mobile بدون نیاز

گاهی یک Row با Wrap و Basis درست، نیاز به Duplicate کردن کل محتوا برای Mobile را از بین می‌برد.

---

## پل به DevTools

در Chrome DevTools کنار Flex Container روی Badge مربوط به `flex` کلیک کن. Overlay جای Childها و Lineها را نشان می‌دهد. سپس در Computed Style این موارد را بررسی کن:

```text
flex-wrap
flex-basis
flex-shrink
min-width
gap
width
```

اگر Wrap رخ نمی‌دهد، فقط به `flex-wrap` خیره نشو؛ معمولاً علت در Basis، Shrink یا Min Size است.

---

## تصویر ذهنی نهایی

Flex Wrap مانند فروشگاهی است که در شلوغی صندوق دوم باز می‌کند. بازشدن صندوق دوم مشکل اندازهٔ سبدها را حل نمی‌کند؛ فقط مسیر تازه‌ای برای صف می‌سازد.

---

## قوانین طلایی

- **«Wrap اجازهٔ خط جدید می‌دهد؛ اندازهٔ Item را تعیین نمی‌کند.»**
- **«قبل از Wrap، Basis، Shrink و Min Size را بررسی کن.»**
- **«Align Items برای Itemهاست؛ Align Content برای Lineها.»**
- **«Flex Wrap جریان می‌سازد؛ Grid شبکه می‌سازد.»**
- **«عرض‌های بین Breakpointها را آزمایش کن؛ شکست‌های واقعی آنجا پنهان‌اند.»**

### منابع رسمی این فصل

- CSS Flexible Box Layout Module Level 1
- Elementor Help: Flexbox Container layout and responsive container behavior
- Chrome DevTools: Flex overlay and CSS badges

# ۹. درک عمیق Grid؛ Track، Line، Cell و Area

## مسئله‌ای که Grid حل می‌کند

گاهی فقط کنار هم گذاشتن عناصر کافی نیست. می‌خواهی:

- ستون‌های چند ردیف دقیقاً هم‌راستا باشند؛
- یک کارت دو ستون را اشغال کند؛
- ارتفاع ردیف‌ها و عرض ستون‌ها یک قرارداد مشترک داشته باشند؛
- جای Itemها نسبت به کل شبکه معنا داشته باشد.

Flexbox صف را خوب مدیریت می‌کند؛ Grid برای نقشهٔ دوبعدی ساخته شده است.

---

## تشبیه به دنیای واقعی: هتل با راهرو و اتاق

یک هتل را تصور کن:

```text
خط 1      خط 2      خط 3      خط 4
  │          │          │          │
──┼──────────┼──────────┼──────────┼── خط افقی 1
  │ اتاق A   │ اتاق B   │ اتاق C   │
──┼──────────┼──────────┼──────────┼── خط افقی 2
  │ اتاق D   │ اتاق E   │ اتاق F   │
──┼──────────┼──────────┼──────────┼── خط افقی 3
```

در این تصویر:

- فاصلهٔ میان دو خط = **Track**
- محل تقاطع یک ردیف و ستون = **Cell**
- چند Cell کنار هم = **Area**
- دیوارهای شماره‌دار = **Grid Line**

Item می‌تواند در یک اتاق بماند یا چند اتاق را به هم وصل کند.

---

## چرا Grid ساخته شد؟

با Flexهای تو‌در‌تو هم می‌توان بسیاری از شبکه‌ها را ساخت، اما ساختار به‌سرعت پیچیده می‌شود:

```text
Row
├── Column
│   ├── Row
│   └── Row
└── Column
    ├── Row
    └── Row
```

Grid اجازه می‌دهد Parent مستقیماً نقشهٔ ردیف و ستون را تعریف کند. Childها روی همان نقشه قرار می‌گیرند.

---

## واژگان اصلی

### Grid Container

Parentی که `display: grid` دارد.

### Grid Item

Child مستقیم Grid Container.

### Track

فضای میان دو Grid Line؛ می‌تواند ستون یا ردیف باشد.

### Cell

کوچک‌ترین خانهٔ حاصل از تقاطع یک ردیف و ستون.

### Area

یک مستطیل متشکل از یک یا چند Cell.

### Gap

فاصلهٔ میان Trackها، نه Padding داخل Itemها.

---

## `fr` چیست؟

`fr` سهمی از فضای باقی‌ماندهٔ Grid است.

```css
grid-template-columns: 1fr 1fr 1fr;
```

سه ستون سهم مساوی از فضای توزیع‌پذیر می‌گیرند.

اما `1fr` به معنی «هر شرایطی دقیقاً یک‌سوم» نیست. Min Content، Gap، Track ثابت و محدودیت Childها می‌توانند اندازهٔ واقعی را تغییر دهند.

برای اینکه Track بتواند واقعاً کوچک شود، گاهی این الگو لازم است:

```css
grid-template-columns: minmax(0, 1fr) minmax(0, 1fr);
```

صفر در اینجا اجازه می‌دهد حداقل Track از Min Content پایین‌تر بیاید؛ البته محتوا همچنان ممکن است نیاز به Wrap یا Overflow Control داشته باشد.

---

## `minmax()`؛ اتاقی با حداقل و حداکثر

```css
grid-template-columns: repeat(3, minmax(220px, 1fr));
```

یعنی هر ستون:

- از ۲۲۰px کوچک‌تر نشود؛
- در صورت وجود فضای بیشتر، تا سهمی از فضای آزاد رشد کند.

عدد ۲۲۰ یا ۲۸۰ قانون جهانی نیست. حداقل باید از محتوای واقعی کارت استخراج شود:

- طول عنوان فارسی
- اندازهٔ دکمه
- قیمت
- Padding
- تصویر
- حداقل خوانایی

---

## `auto-fill` و `auto-fit`؛ اتاق‌های خالی هتل

فرض کن هتل می‌تواند چهار اتاق در یک ردیف بسازد، اما فقط دو مهمان دارد.

### `auto-fill`

اتاق‌های ممکن را حفظ می‌کند؛ حتی اگر بعضی خالی باشند.

```text
[مهمان][مهمان][خالی][خالی]
```

### `auto-fit`

Trackهای خالی را جمع می‌کند و فضای آن‌ها را به Trackهای موجود می‌دهد.

```text
[     مهمان     ][     مهمان     ]
```

الگوی رایج:

```css
grid-template-columns: repeat(auto-fit, minmax(16rem, 1fr));
```

اما «همیشه auto-fit» قانون درستی نیست. اگر حفظ جای ستون‌های خالی برای Alignment یا ریتم شبکه مهم باشد، `auto-fill` می‌تواند انتخاب مناسب‌تری باشد.

---

## رفتار در سه عرض

فرض کن حداقل کارت ۲۸۰px و Gap برابر ۲۴px است.

### عرض ۱۲۰۰px

```text
[ کارت ][ کارت ][ کارت ][ کارت ]
```

### عرض ۷۶۰px

```text
[      کارت      ][      کارت      ]
[      کارت      ][      کارت      ]
```

### عرض ۳۶۰px

```text
[          کارت          ]
[          کارت          ]
[          کارت          ]
```

Grid در این الگو بدون Breakpoint صریح، تعداد Trackهای قابل جاگیری را تغییر می‌دهد. بااین‌حال هنوز باید عرض‌های میانی و محتوای بلند را آزمایش کنی.

---

## Flex Item داخل Grid و Grid Item داخل Flex

یک Element می‌تواند هم‌زمان دو نقش داشته باشد:

```text
نسبت به Parent خودش: Grid Item
نسبت به Childهای خودش: Flex Container
```

مثلاً کارت محصول در شبکه:

```text
Product Grid  ← Grid Container
└── Product Card  ← Grid Item + Flex Container
    ├── Image
    ├── Content
    └── Button
```

نقش بیرونی می‌گوید کارت در شبکه کجا و با چه اندازه‌ای قرار گیرد. موتور داخلی می‌گوید محتویات کارت چگونه چیده شوند. این دو را با هم قاطی نکن.

---

## در Elementor V4

Grid Container را زمانی انتخاب کن که Trackهای مشترک واقعاً ارزش دارند. در پنل Layout:

- تعداد یا تعریف ستون‌ها
- ردیف‌ها
- Gap
- Alignment
- Placement و Span Itemها

را کنترل کن.

برای یک شبکهٔ کارت، ابتدا Auto Placement را امتحان کن. جای‌گذاری دستی همه Itemها معمولاً سیستم را شکننده می‌کند. Placement دستی را برای Hero Card، Featured Item یا ترکیب خاص نگه دار.

اگر رابط امکان واردکردن تعریف سفارشی Track را می‌دهد، خروجی را در DevTools بررسی کن. نام کنترل رابط و CSS نهایی همیشه نباید یکسان فرض شود.

---

## Grid یا Flex Wrap؟

```text
فقط جریان و شکستن خط مهم است؟ → Flex Wrap
تراز ستون‌ها در چند ردیف مهم است؟ → Grid
Item باید Span کند؟ → Grid
ترتیب خطی محتوا مهم‌ترین چیز است؟ → Flex را ابتدا بررسی کن
```

---

## اشتباهات رایج

- استفاده از Grid برای یک ردیف ساده
- فرض اینکه `1fr` هر محتوایی را مجبور به کوچک‌شدن می‌کند
- Placement دستی تمام Itemها
- ساخت Track با حداقل ثابت بدون آزمایش متن فارسی
- تغییر ترتیب بصری برخلاف ترتیب DOM
- گذاشتن Height ثابت روی ردیف‌هایی با محتوای پویا

---

## پل به DevTools

در Elements Panel روی Badge مربوط به `grid` کلیک کن. Overlay می‌تواند:

- شماره Lineها
- Trackها
- Gapها
- Areaها

را نشان دهد. این بهترین راه برای دیدن تفاوت Line و Cell است.

---

## تصویر ذهنی نهایی

Flex مثل صف مسافران است؛ Grid مثل نقشهٔ اتاق‌های هتل. در صف، ترتیب حرکت مهم است. در هتل، جای اتاق نسبت به ردیف و ستون معنا دارد.

---

## قوانین طلایی

- **«Grid را با Track طراحی کن، نه با هل‌دادن تک‌تک Itemها.»**
- **«`fr` سهم فضای باقی‌مانده است، نه تضمین اندازهٔ مطلق.»**
- **«حداقل `minmax()` را از نیاز محتوا استخراج کن، نه از عدد جادویی.»**
- **«Auto-fit Track خالی را جمع می‌کند؛ Auto-fill آن را نگه می‌دارد.»**
- **«نقش Item در Parent و موتور Layout داخلی آن دو تصمیم جدا هستند.»**

### منابع رسمی این فصل

- CSS Grid Layout Module Level 1/2
- Elementor Help: Grid Container layout options
- Chrome DevTools: Grid overlays and badges

# ۱۰. درک عمیق Typography؛ متن فقط Font نیست

## مسئله‌ای که Typography حل می‌کند

کاربر پیش از دیدن دکمه، رنگ و تصویر، باید متن را بفهمد. اگر متن:

- بیش از حد متراکم باشد؛
- خط‌های خیلی بلند داشته باشد؛
- سلسله‌مراتب نامشخصی داشته باشد؛
- در Mobile بشکند؛
- یا وزن‌های فونت درست Load نشوند؛

زیباترین Layout هم قابل استفاده نخواهد بود.

Typography فقط انتخاب نام یک Font نیست. Typography **معماری خواندن** است.

---

## تشبیه به دنیای واقعی: موسیقی و نفس‌کشیدن

یک قطعه موسیقی را تصور کن:

- Font Family = جنس صدای ساز
- Font Size = شدت صدا
- Font Weight = تأکید نوازنده
- Line Height = فاصلهٔ ضرب‌ها و فرصت نفس‌کشیدن
- Paragraph Spacing = مکث میان جمله‌های موسیقی
- Headingها = بخش‌های اصلی قطعه
- Width ستون = طول هر عبارت پیش از نفس بعدی

اگر همهٔ نت‌ها با یک شدت و بدون مکث اجرا شوند، حتی موسیقی خوب خفه‌کننده می‌شود.

---

## چرا Typography چند تصمیم هم‌زمان است؟

خوانایی از تعامل چند عامل به وجود می‌آید:

```text
Font Family
+ Font Size
+ Font Weight
+ Line Height
+ Line Length
+ Contrast
+ Spacing
+ Language Script
```

برای فارسی، شکل حروف، اتصال‌ها، نقطه‌ها و ارتفاع بصری ممکن است با فونت لاتین متفاوت باشد. بنابراین نسخهٔ ظاهراً مناسب یک Scale لاتین را نباید بدون آزمایش روی متن واقعی فارسی پذیرفت.

---

## نقش معنایی و ظاهر را جدا کن

`h1` یا `h2` فقط برای بزرگ‌کردن متن نیست. Heading ساختار سند را تعریف می‌کند.

```text
H1: عنوان اصلی صفحه
H2: بخش‌های اصلی
H3: زیربخش‌ها
Paragraph: متن توضیحی
List: مجموعهٔ آیتم‌های مرتبط
```

ظاهر می‌تواند با Class تغییر کند، اما نقش معنایی باید درست بماند.

در Elementor V4، Level یا نوع Element را در General/Content و ظاهر را در Style مدیریت کن.

---

## Line Height؛ فضای تنفس عمودی

Line Height خیلی کم باعث برخورد بصری سطرها می‌شود. خیلی زیاد، پیوند جمله‌ها را از بین می‌برد.

برای متن بدنه معمولاً Line Height نسبی بهتر از عدد ثابت پیکسلی است:

```css
line-height: 1.7;
```

عدد مناسب به فونت، اندازه و زبان وابسته است. برای فارسی باید با پاراگراف واقعی، اعداد، پرانتز، لینک و کلمات لاتین ترکیبی آزمایش شود.

---

## طول خط

ستون بسیار عریض چشم را مجبور می‌کند مسیر طولانی طی کند و پیدا کردن آغاز خط بعد سخت می‌شود.

می‌توان با `max-inline-size` طول خط را کنترل کرد:

```css
.article-text {
  max-inline-size: 42rem;
}
```

واحد `ch` می‌تواند برای تخمین طول خط مفید باشد، اما بر اساس عرض نویسهٔ صفر لاتین محاسبه می‌شود؛ پس برای فارسی معیار دقیق نیست. اگر از `60ch` استفاده می‌کنی، نتیجه را با فونت واقعی فارسی بررسی کن.

---

## Typography سیال با `clamp()`

به‌جای جهش ناگهانی Font Size در چند Breakpoint، می‌توان اندازه را در یک بازه سیال کرد:

```css
font-size: clamp(1.75rem, 1.2rem + 2vw, 3.5rem);
```

تصویر ذهنی:

```text
حداقل ← اندازهٔ سیال با عرض صفحه ← حداکثر
```

- مقدار اول اجازه نمی‌دهد متن بیش از حد کوچک شود.
- مقدار میانی باعث رشد سیال می‌شود.
- مقدار آخر جلوی بزرگ‌شدن بی‌نهایت را می‌گیرد.

`clamp()` معجزه نیست. باید در عرض‌های بسیار کوچک، بسیار بزرگ و با متن طولانی آزمایش شود.

---

## Scale تایپوگرافی

به‌جای Font Sizeهای پراکنده:

```text
17px
21px
29px
34px
43px
```

یک Scale محدود تعریف کن:

```text
text-sm
text-md
text-lg
heading-sm
heading-md
heading-lg
```

این نام‌ها می‌توانند Variable یا بخشی از Global Class باشند. هدف این است که هر عدد تصادفی تبدیل به تصمیمی قابل ردیابی شود.

---

## در Elementor V4

برای Typography این سؤال‌ها را بپرس:

1. نقش معنایی Element چیست؟
2. Style باید Local باشد یا Global؟
3. Font Family، Size یا Color باید Variable باشد؟
4. آیا State مثل Hover برای Link تعریف شده است؟
5. آیا Mobile فقط Font کوچک‌تر می‌خواهد یا Width و Line Height نیز باید تغییر کنند؟
6. آیا فونت و Weight انتخاب‌شده واقعاً در Frontend Load می‌شوند؟

Typography یک Heading تکرارشونده معمولاً بهتر است با Global Class و Variableهای محدود مدیریت شود، نه با تنظیم جداگانهٔ ده‌ها Heading.

---

## مثال واقعی: Hero فارسی

عنوان کوتاه در طراحی اولیه:

```text
آینده را بسازید
```

اما عنوان واقعی ممکن است باشد:

```text
زیرساخت یکپارچه برای مدیریت هوشمند عملیات سازمانی
```

اگر فقط با متن کوتاه تست کرده باشی:

- ارتفاع Hero تغییر می‌کند؛
- دکمه‌ها پایین می‌روند؛
- تصویر از تراز خارج می‌شود؛
- در ۷۶۸px یک کلمه تنها می‌ماند.

پس تست Typography باید شامل کوتاه‌ترین و بلندترین محتوای واقعی باشد.

---

## پل به DevTools

در Computed Style این موارد را ببین:


---

## اشتباهات رایج

- استفاده از Heading فقط برای بزرگ‌کردن متن
- اندازه‌های پراکنده بدون Scale

- کوچک‌کردن افراطی متن Mobile برای جا دادن Layout اشتباه

---

## تصویر ذهنی نهایی

Typography مثل موسیقی است. Font جنس صداست، اما ریتم خواندن را فاصله، طول خط، وزن و سلسله‌مراتب می‌سازند.

# ۱۱. درک عمیق Image، SVG، Background و Aspect Ratio

## مسئله‌ای که این مفهوم حل می‌کند

همهٔ چیزهایی که شبیه تصویر دیده می‌شوند نقش یکسان ندارند.

- تصویر محصول بخشی از محتواست.
- بافت طلایی پشت Hero تزئینی است.
- لوگو ممکن است SVG باشد.
- عکس کارت باید Crop شود.
- Hero Image ممکن است عنصر LCP باشد.

انتخاب اشتباه میان Image و Background روی Accessibility، Responsive، Performance و نگهداری اثر می‌گذارد.

---

## تشبیه به دنیای واقعی: عکس قاب‌شده و کاغذدیواری

یک اتاق را تصور کن:

- عکس خانوادگی داخل قاب، معنای مستقل دارد؛ اگر حذف شود بخشی از محتوا از بین می‌رود. این **Image Element** است.
- طرح روی دیوار فقط فضا را زیباتر می‌کند؛ اگر حذف شود پیام اصلی هنوز باقی است. این **Background** است.
- نقشهٔ معماری که با خطوط رسم شده و در هر اندازه واضح است، شبیه **SVG** است.

---

## Image یا Background؟

از خودت بپرس:

> اگر تصویر Load نشود، آیا کاربر بخشی از اطلاعات را از دست می‌دهد؟

اگر بله، معمولاً Image Element و متن جایگزین مناسب لازم است.

اگر تصویر صرفاً تزئینی است، Background می‌تواند درست‌تر باشد.

این قانون مطلق نیست، اما نقطهٔ شروع قابل دفاعی است.

---

## Aspect Ratio؛ شکل قاب پیش از رسیدن عکس

مرورگر باید بداند جعبهٔ تصویر چه شکلی است. اگر تا Load شدن فایل هیچ فضایی رزرو نشود، محتوا بعداً جابه‌جا می‌شود.

```css
.media {
  aspect-ratio: 4 / 3;
}
```

این یعنی حتی پیش از Load کامل تصویر، Box نسبت ۴ به ۳ دارد.

برای `<img>`، تعیین `width` و `height` واقعی نیز به مرورگر کمک می‌کند نسبت را از ابتدا محاسبه کند.

---

## `object-fit`؛ عکس چگونه داخل قاب بنشیند؟

### `cover`

قاب کاملاً پر می‌شود؛ بخشی از تصویر ممکن است Crop شود.

### `contain`

تمام تصویر دیده می‌شود؛ ممکن است اطراف آن فضای خالی بماند.

### `object-position`

نقطهٔ کانونی Crop را تعیین می‌کند.

مثلاً اگر چهره در سمت راست عکس است، `center center` شاید صورت را ببرد. باید موقعیت را متناسب با سوژه تنظیم کنی.

---

## SVG چیست؟

SVG به‌جای شبکه‌ای از Pixelها، شکل را با مسیرها و بردارها توصیف می‌کند. برای آیکون، لوگو و Illustration خطی مناسب است.

اما «SVG همیشه سبک است» درست نیست. یک SVG پیچیده می‌تواند:

- هزاران Path داشته باشد؛
- Filter سنگین اجرا کند؛
- کد یا Metadata اضافی داشته باشد؛
- از نظر امنیت نیازمند Sanitization باشد.

`viewBox` باید درست باشد تا مقیاس‌پذیری قابل پیش‌بینی بماند.

---

## Responsive Images

یک تصویر ۲۵۰۰px برای کارت ۳۲۰px اتلاف پهنای باند است. مرورگر با `srcset` و `sizes` می‌تواند نسخه مناسب‌تری انتخاب کند.

در WordPress و Elementor معمولاً اندازه‌های مختلف Media Library در این فرایند نقش دارند، اما باید در Network Panel بررسی کنی چه فایل واقعی دانلود شده است.

---

## Lazy Loading و تصویر LCP

تصاویر پایین صفحه معمولاً می‌توانند Lazy Load شوند.

اما تصویر اصلی بالای صفحه که احتمالاً LCP است، نباید بی‌دلیل Lazy Load شود؛ چون شروع دانلود آن عقب می‌افتد.

تصویر ذهنی:

```text
زیر Fold → دیرتر بارگذاری‌شدن معمولاً مفید
تصویر اصلی Hero → باید زود کشف و دانلود شود
```

---

## در Elementor V4

برای هر تصویر این قرارداد را ثبت کن:

```text
Role: content / decorative
Source: media / dynamic
Aspect ratio: 16:9
Fit: cover
Focal point: inline-start center
Alt: meaningful / empty for decorative equivalent
Responsive source: verified
Loading priority: above-fold / below-fold
```

Background را روی Box مسئول تزئین قرار بده. اگر یک Wrapper فقط برای نگه‌داشتن Background ساخته‌ای، بپرس آیا همان Parent موجود می‌تواند این مسئولیت را بگیرد یا نه.

---

## مثال واقعی: کارت محصول

```text
Product Card
├── Media Box (aspect-ratio: 4/3)
│   └── Product Image (object-fit: cover)
├── Title
├── Price
└── Button
```

اگر تصویر Dynamic خالی بود:

- Fallback Image داری؟
- Media Box باید پنهان شود؟
- Gap باقی می‌ماند؟
- ارتفاع کارت‌ها از هم جدا می‌شود؟

این دیگر فقط موضوع تصویر نیست؛ Dynamic Data و Layout نیز دخیل‌اند.

---

## پل به DevTools

در Network Panel ببین کدام فایل تصویر دانلود شده و اندازه آن چقدر است. در Elements/Computed این موارد را بررسی کن:

```text
width / height
aspect-ratio
object-fit
object-position
background-size
background-position
```

برای CLS، گزینهٔ Layout Shift Regions در DevTools می‌تواند جابه‌جایی‌ها را نشان دهد.

---

## اشتباهات رایج

- Background برای تصویر محتوایی
- Alt نامناسب یا تکرار متن اطراف
- نداشتن ابعاد اولیه
- `cover` بدون نقطه کانونی
- Lazy Load روی Hero Image
- فایل بسیار بزرگ برای نمایش کوچک
- فرض سبک و امن بودن هر SVG
- ساخت Duplicate Image برای هر Device بدون نیاز واقعی

---

## تصویر ذهنی نهایی

Image عکس قاب‌شده است؛ Background کاغذدیواری. Aspect Ratio قبل از رسیدن عکس، جای قاب را نگه می‌دارد و Object Fit تعیین می‌کند عکس چگونه داخل آن بنشیند.

---

## قوانین طلایی

- **«محتوا را Image کن؛ تزئین را Background.»**
- **«Aspect Ratio شکل Box را می‌سازد؛ Object Fit تصویر داخل آن را جا می‌دهد.»**
- **«فضای تصویر را از ابتدا رزرو کن تا صفحه نپرد.»**
- **«تصویر LCP را بی‌دلیل Lazy Load نکن.»**
- **«SVG برداری است، اما خودبه‌خود سبک و امن نیست.»**

# ۱۲. درک عمیق Position؛ Flow، مرجع مختصات و Overlay

## مسئله‌ای که Position حل می‌کند

گاهی یک Badge باید روی گوشهٔ تصویر قرار گیرد، یک دکمه باید به Viewport بچسبد یا عنوان بخش باید هنگام Scroll باقی بماند.

اما اگر Position را بدون فهم Normal Flow استفاده کنی، متن روی هم می‌افتد، Parent ارتفاعش را از دست می‌دهد و Responsive به مجموعه‌ای از Offsetهای تصادفی تبدیل می‌شود.

---

## تشبیه به دنیای واقعی: صف، استیکر و شیشهٔ اتوبوس

- `static` = فردی که در صف عادی ایستاده است.
- `relative` = فردی که جای خود را در صف حفظ کرده ولی کمی کنار رفته؛ همچنین می‌تواند تابلوی مرجع اطراف خود بسازد.
- `absolute` = استیکری که از صف خارج شده و به نزدیک‌ترین سطح مرجع می‌چسبد.
- `fixed` = برچسبی روی شیشهٔ اتوبوس؛ خیابان حرکت می‌کند اما برچسب نسبت به شیشه ثابت است.
- `sticky` = یادداشت چسبانی که با کاغذ حرکت می‌کند تا به لبهٔ میز برسد و سپس در محدودهٔ همان کاغذ می‌ماند.

---

## Normal Flow چیست؟

Normal Flow روش پیش‌فرض مرورگر برای قرار دادن Boxهاست. Blockها معمولاً زیر هم و Inlineها در جریان متن قرار می‌گیرند. Flex و Grid نیز جریان‌های سازمان‌یافته‌اند.

محتوای اصلی صفحه باید تا جای ممکن در Flow بماند، چون:

- Parent ارتفاع واقعی می‌گیرد؛
- متن بلند فضا را گسترش می‌دهد؛
- عناصر بعدی هل داده می‌شوند؛
- Responsive طبیعی‌تر است.

---

## `position: relative`

Relative دو نقش مهم دارد:

1. Element در Flow باقی می‌ماند و جای اولیه‌اش رزرو می‌شود.
2. می‌تواند Containing Block فرزند Absolute را بسازد.

اگر فقط برای مرجع‌کردن Parent از Relative استفاده می‌کنی، لازم نیست خود Parent را با `top` یا `left` جابه‌جا کنی.

---

## `position: absolute`

Absolute از Normal Flow خارج می‌شود. دیگر به Parent برای محاسبه ارتفاع کمک نمی‌کند.

مختصات آن نسبت به **Containing Block** محاسبه می‌شوند. این مرجع همیشه Body نیست. معمولاً نزدیک‌ترین Ancestor مناسب و Position‌شده مرجع می‌شود، اما Transform و بعضی ویژگی‌های دیگر نیز می‌توانند Containing Block بسازند.

پس جملهٔ درست این نیست:

> Absolute به Body می‌چسبد.

بلکه:

> Absolute مختصاتش را از Containing Block خود می‌گیرد؛ اگر مرجع مورد انتظار ساخته نشده باشد، ممکن است نتیجه بسیار دورتر از کارت دیده شود.

---

## `position: fixed`

Fixed معمولاً نسبت به Viewport قرار می‌گیرد؛ مثل دکمهٔ بازگشت به بالا.

اما بعضی Ancestorهای Transform‌شده یا دارای ویژگی‌های خاص می‌توانند رفتار مرجع Fixed را تغییر دهند. پس «هیچ Parentی روی Fixed اثر ندارد» قانون دقیقی نیست.

---

## `position: sticky`

Sticky ترکیبی از Flow و چسبیدن است:

- ابتدا در Flow عادی است؛
- وقتی به Inset تعیین‌شده مثل `top: 0` می‌رسد، می‌چسبد؛
- در محدودهٔ Scroll Container و Parent خودش باقی می‌ماند.

Sticky معمولاً بدون Inset مشخص، چیزی برای چسبیدن ندارد.

Ancestor دارای `overflow` می‌تواند Scroll Container متفاوتی بسازد و Sticky را برخلاف انتظار محدود کند.

---

## در Elementor V4

برای Overlay کارت:

```text
Card Stage: position relative
├── Image: normal flow
├── Content: normal flow
└── Badge: position absolute; inset-block-start: 16px; inset-inline-end: 16px
```

این معماری می‌گوید فقط Badge شناور است؛ تصویر و متن همچنان ارتفاع کارت را می‌سازند.

برای Hero پیچیده نیز بهتر است یک Visual Stage اختصاصی داشته باشی. Nodeهای تزئینی Absolute را فقط داخل همان Stage قرار بده، نه در کل Section.

---

## Flow در برابر Overlay

```text
آیا عنصر بخشی از محتوای اصلی است؟
→ ابتدا در Flow نگه دار

آیا فقط تزئینی یا شناور است؟
→ Absolute را بررسی کن

آیا باید هنگام Scroll نسبت به Viewport بماند؟
→ Fixed یا Sticky را با توجه به محدوده بررسی کن
```

---

## RTL و Insetهای منطقی

به‌جای `left` و `right` می‌توان در بسیاری از سناریوها از Logical Insetها استفاده کرد:

```css
inset-inline-end: 1rem;
inset-block-start: 1rem;
```

این Badge را در «پایان محور Inline» قرار می‌دهد و با RTL/LTR سازگارتر است.

---

## اشتباهات رایج

- Absolute کردن متن اصلی
- Offsetهای ثابت برای جبران Tree اشتباه
- Parent بدون مرجع واضح
- فرض اینکه مرجع همیشه Body است
- Sticky بدون `top` یا داخل Overflow نامناسب
- Height ثابت روی Stage با محتوای متغیر
- استفاده از Position برای چیزی که Flex/Grid حل می‌کند

---

## پل به DevTools

در Computed Style این موارد را بررسی کن:

```text

inset / top / right / bottom / left
containing block clues
transform on ancestors
overflow on ancestors
```

Outline موقت روی Parentها بگذار تا مرز Stage و Containing Block را ببینی.

---

## تصویر ذهنی نهایی

Flow صف آدم‌هاست. Absolute از صف بیرون می‌آید و مانند استیکر به یک سطح مرجع می‌چسبد. اگر سطح مرجع را اشتباه انتخاب کنی، استیکر گم نمی‌شود؛ فقط به دیوار دیگری چسبیده است.

---

## قوانین طلایی

- **«Relative در Flow می‌ماند؛ Absolute از Flow خارج می‌شود.»**
- **«مختصات بدون Containing Block معنا ندارند.»**
- **«محتوای اصلی را با Position نساز؛ Overlay هدفمند را با Position بساز.»**
- **«Sticky هم Inset می‌خواهد، هم فضای Scroll و هم Parent مناسب.»**
- **«Position و Z-index دو مسئلهٔ جدا هستند.»**

- Elementor Help: Position controls
- CSS Overflow specification

# ۱۳. درک عمیق Z-index، Stacking Context و Overflow

## مسئله‌ای که این مفهوم حل می‌کند

یک Badge را `z-index: 999999` می‌کنی اما هنوز زیر Header است. یک Dropdown روی همه چیز جلوست ولی بخشی از آن بریده می‌شود. یک Parent دارای Transform باعث می‌شود Modal رفتار عجیبی پیدا کند.

مشکل این است که Z-index یک جدول جهانی از اعداد نیست.

---

## تشبیه به دنیای واقعی: ساختمان‌ها و طبقه‌ها

دو ساختمان کنار هم را تصور کن:

```text
ساختمان A        ساختمان B
طبقه 999         طبقه 2
```

شمارهٔ طبقه فقط داخل همان ساختمان معنا دارد. اگر کل ساختمان B روی سکوی بالاتری قرار گرفته باشد، طبقهٔ ۲ آن می‌تواند جلوی طبقهٔ ۹۹۹ ساختمان A دیده شود.

هر ساختمان یک **Stacking Context** است.

---

## Stacking Context چیست؟

Stacking Context یک فضای مستقل برای ترتیب Paint است. Childهای داخل آن ابتدا با هم مرتب می‌شوند و سپس کل Context به‌عنوان یک واحد نسبت به Contextهای هم‌سطح قرار می‌گیرد.

تصویر:

```text
Root Context
├── Header Context (z: 10)
│   └── Icon (z: 1)
└── Main Context (z: 1)
    └── Badge (z: 9999)
```

Badge با عدد ۹۹۹۹ داخل Main نمی‌تواند الزاماً از Header Context با z برابر ۱۰ عبور کند؛ چون ابتدا جای خود Main Context مقایسه می‌شود.

---

## چه چیزهایی Context می‌سازند؟

بسته به شرایط، مواردی مانند این‌ها می‌توانند Stacking Context جدید بسازند:

- Position همراه Z-index غیر Auto
- `opacity` کمتر از ۱
- `transform`
- `filter`
- `isolation: isolate`
- بعضی حالت‌های Flex/Grid Item با Z-index
- Top Layer برای Dialog و Popoverهای خاص

هدف حفظ‌کردن تمام فهرست نیست. هدف این است که وقتی Z-index بی‌اثر شد، Ancestorها را بررسی کنی.

---

## Paint Order و Z-index

مرورگر فقط عدد Z-index را نگاه نمی‌کند. Background Parent، Elementهای Flow، Positioned Elementها و Contextها ترتیب Paint مشخصی دارند.

پس گاهی Element بدون Z-index به‌دلیل Paint Order بعدی جلوتر دیده می‌شود؛ و گاهی Z-index فقط پس از Position یا در نقش خاص Item اثر مورد انتظار را دارد.

---

## Overflow؛ قیچی Parent

`overflow: hidden` فقط Scrollbar را پنهان نمی‌کند. محتوای بیرون مرز را Clip می‌کند.

```text
Parent با Overflow Hidden
┌──────────────────┐
│          Badge   │── بخش بیرون‌زده بریده می‌شود
└──────────────────┘
```

حتی اگر Badge Z-index بالایی داشته باشد، نمی‌تواند از قیچی همان Clip عبور کند.

این دو سؤال جدا هستند:

1. Element از نظر لایه جلوست یا عقب؟
2. Element اجازه دارد خارج مرز Ancestor دیده شود یا نه؟

---

## درخت عیب‌یابی Z-index

```text
آیا Element واقعاً overlap دارد؟
↓
Position/role آن چیست؟
↓
Stacking Context خودش کدام است؟
↓
کدام Ancestor Context جدید ساخته؟
↓
Contextهای sibling چه ترتیبی دارند؟
↓
آیا Overflow یا Clip آن را می‌بُرد؟
↓
آیا عنصر باید در Top Layer/Portal دیگری باشد؟
```

---

## در Elementor V4

برای یک Stage تصویری:

```text
Visual Stage: position relative; isolation isolate
├── Background shape: z 0
├── Main image: z 1
├── Decorative nodes: z 2
└── Badge: z 3
```

`isolation: isolate` می‌تواند عمداً Context محلی بسازد تا عددهای لایه‌بندی داخل Stage به بیرون نشت مفهومی نداشته باشند.

اما Dropdown، Tooltip یا Modal شاید نباید داخل Parent دارای Overflow Hidden زندانی شود. ساختار Element Tree در اینجا مهم‌تر از افزایش عدد است.

---

## Top Layer

بعضی عناصر بومی مانند Dialog بازشده به‌صورت Modal وارد Top Layer مرورگر می‌شوند. Top Layer بالاتر از Stacking Contextهای عادی Document قرار می‌گیرد و Z-index عادی منطق آن را کنترل نمی‌کند.

این مفهوم نشان می‌دهد چرا «همه چیز با 999999 حل می‌شود» از پایه اشتباه است.

---

## اشتباهات رایج

- عددهای نجومی بدون تحلیل Context
- Transform روی Parent بدون توجه به Context جدید
- Overflow Hidden برای حذف Scrollbar و بریدن Dropdown
- قرار دادن Modal داخل Stage محلی
- تصور اینکه Child می‌تواند سقف Context Parent را بشکند
- استفاده از Z-index برای حل ترتیب DOM یا Layout اشتباه

---

## پل به DevTools

- Ancestorها را در Elements Panel بالا برو.
- در Computed، `transform`، `opacity`، `position`، `z-index` و `overflow` را بررسی کن.
- Layers Panel یک نمای سه‌بعدی از Composition می‌دهد، اما Layer Compositing دقیقاً همان Stacking Context نیست؛ آن را ابزار کمکی بدان، نه تعریف مفهوم.

---

## تصویر ذهنی نهایی

Z-index شماره طبقه است، نه ارتفاع جهانی از زمین. ابتدا ببین در کدام ساختمان هستی؛ سپس شماره طبقه را مقایسه کن. Overflow هم نگهبانی است که حتی طبقهٔ بالا را از پنجره بیرون نمی‌گذارد.

---

## قوانین طلایی

- **«Z-index را داخل Stacking Context بخوان.»**
- **«Child با عدد بزرگ نمی‌تواند همیشه از Context Parent فرار کند.»**
- **«Overflow می‌تواند Element جلویی را هم Clip کند.»**
- **«اول درخت لایه‌ها را اصلاح کن، بعد عدد را.»**
- **«Modal و Dropdown را در Context مناسب قرار بده، نه در زندان Stage.»**

### منابع رسمی این فصل

- CSS Positioned Layout and Painting/Stacking rules
- Chrome DevTools Layers and Top Layer references
- Elementor Help: Position and overflow controls

# ۱۴. درک عمیق Responsive؛ Inheritance، Override و Breakpoint

## مسئله‌ای که Responsive حل می‌کند

Responsive یعنی یک Layout بتواند با فضای متفاوت، محتوای متفاوت و روش تعامل متفاوت سازگار شود.

Responsive فقط این نیست که Desktop را کوچک کنی. گاهی در Mobile:

- Direction عوض می‌شود؛
- اولویت محتوا تغییر می‌کند؛
- دکمه تمام‌عرض می‌شود؛
- Grid ستون کمتری می‌گیرد؛
- Typography سیال می‌شود؛
- تزئین حذف می‌شود.

---

## تشبیه به دنیای واقعی: آبشار و سدها

Desktop را سرچشمهٔ آبشار تصور کن. مقدارها به مراحل پایین‌تر می‌ریزند:

```text
Desktop
  ↓
Tablet
  ↓
Mobile
```

تا وقتی در Tablet یا Mobile مقدار مستقل نسازی، آب از بالا ادامه پیدا می‌کند.

وقتی در Mobile عدد تازه‌ای وارد می‌کنی، مثل ساختن سد است:

```text
Desktop: 40px
Tablet: inherit
Mobile: 16px ← سد محلی
```

اگر Mobile را نیز دستی روی 40px بگذاری، ظاهراً فعلاً با Desktop برابر است، اما دیگر به Desktop متصل نیست. اگر Desktop بعداً 48px شود، Mobile همچنان 40px می‌ماند.

---

## Reset یعنی شکستن سد

اگر می‌خواهی Mobile دوباره از مقدار بالاتر پیروی کند، عدد Desktop را در Mobile کپی نکن. مقدار صریح Mobile را Reset یا پاک کن.

این کار DOM را سبک‌تر نمی‌کند؛ موضوع اصلی **سادگی Cascade و نگهداری** است.

قانون:

> مقدار صریح را فقط وقتی بساز که واقعاً تفاوت رفتاری لازم است.

---

## Breakpoint چیست؟

Breakpoint مرزی است که در آن مجموعه‌ای از Styleها فعال می‌شوند. اما Breakpoint نباید از نام دستگاه نتیجه‌گیری شود.

بهتر است بپرسی:

> Layout در چه عرضی دیگر قرارداد فعلی را حفظ نمی‌کند؟

ممکن است Hero در ۸۷۰px بشکند، نه دقیقاً در عددی که نام Tablet دارد.

Breakpointهای سفارشی Elementor باید از تنظیمات واقعی سایت خوانده شوند؛ نباید عددهای فرضی را قانون جزوه معرفی کرد.

---

## Responsive Contract

برای هر Section، قبل از واردکردن عددها یک قرارداد بنویس:

```text
Desktop:
- Hero row
- Copy 55%
- Visual 45%

Tablet:
- Hero row فشرده
- Gap کمتر
- Heading سیال

Mobile:
- Hero column
- Copy اول
- Button تمام‌عرض
- تزئین محدود
```

این Contract تصمیم را توضیح می‌دهد. اعداد سپس برای اجرای آن می‌آیند.

---

## Fluid Typography و Spacing

Responsive همیشه نیازمند چند جهش Breakpoint نیست. برای مقیاس سیال می‌توان از `clamp()` استفاده کرد:

```css
padding-inline: clamp(1rem, 4vw, 5rem);
font-size: clamp(2rem, 1.25rem + 3vw, 4.5rem);
```

اما اگر ساختار باید از Row به Column تغییر کند، `clamp()` جای Media Query یا کنترل Responsive را نمی‌گیرد.

---

## Container Queries؛ Component به فضای خودش نگاه می‌کند

Media Query به Viewport نگاه می‌کند. Container Query به اندازهٔ Container نزدیک Component نگاه می‌کند.

کارت ممکن است در دو جای سایت باشد:

```text
Hero Wide Area: 700px
Sidebar: 320px
```

Viewport در هر دو یکسان است، اما فضای کارت متفاوت است. Container Query می‌تواند کارت را براساس فضای واقعی خودش تغییر دهد.

```css
.card-region {
  container-type: inline-size;
}

@container (min-width: 36rem) {
  .card {
    grid-template-columns: 12rem 1fr;
  }
}
```

Container Query جایگزین کامل Media Query نیست؛ مکمل آن است.

در مستندات رسمی بررسی‌شده، کنترل بصری Native قطعی برای Container Query در پنل V4 اثبات نشده است. بنابراین این بخش باید به‌عنوان CSS پیشرفته با Custom CSS و تست نسخه هدف ارائه شود.

---

## در Elementor V4

وقتی Device Mode را عوض می‌کنی:

1. ببین کدام Property Indicator نشان می‌دهد مقدار از کجا آمده است.
2. فقط تفاوت لازم را Override کن.
3. اگر تفاوت دیگر لازم نیست، Reset کن.
4. Class درست و State درست را انتخاب کن.
5. Frontend واقعی را آزمایش کن؛ Preview Editor تنها شاهد کافی نیست.

Custom CSS نیز می‌تواند Device-specific و State-specific باشد، پس منبع Style را دقیق دنبال کن.

---

## سناریوی واقعی: Grid کارت‌ها

Desktop:

```text
4 columns
```

Tablet:

```text
2 columns
```

Mobile:

```text
1 column
```

اما اگر از `auto-fit/minmax()` استفاده می‌کنی، ممکن است برخی تغییرها بدون Breakpoint رخ دهند. باید تصمیم بگیری کنترل صریح ۴→۲→۱ مهم‌تر است یا جریان سیال براساس حداقل عرض کارت.

---

## اشتباهات رایج

- کپی عدد Desktop در Mobile به‌جای Reset
- ساخت Override برای هر Property
- انتخاب Breakpoint فقط بر اساس نام Device
- تست‌نکردن عرض‌های میانی
- مخفی‌کردن محتوا به‌جای بازطراحی Layout
- ساخت نسخهٔ Duplicate Desktop/Mobile بدون نیاز
- کوچک‌کردن متن برای پنهان‌کردن مشکل Width
- فرض Native بودن Container Query در Elementor بدون تست

---

## پل به DevTools

Device Toolbar را باز کن و عرض را پیوسته تغییر بده، نه فقط Presetها را. در Styles Panel Media Query فعال و Computed Value را ببین. برای Container Query نیز Badge و Overlay مربوط به Container در نسخه‌های پشتیبان DevTools مفید است.

---

## تصویر ذهنی نهایی

Responsive مثل آبشاری است که مقدارها از بالا جاری می‌شوند. Override سد محلی است. هر سد باید دلیل داشته باشد؛ و وقتی دلیل از بین رفت، باید سد را برداری، نه اینکه آب را با سطل شبیه سرچشمه کنی.

---

## قوانین طلایی

- **«Responsive یعنی تغییر قرارداد Layout، نه فقط کوچک‌کردن همه‌چیز.»**
- **«مقدار برابر با Desktop را در Mobile تکرار نکن؛ اگر تفاوتی لازم نیست، Override را Reset کن.»**
- **«Breakpoint را از نقطه شکست Layout استخراج کن، نه از نام دستگاه.»**
- **«Media Query به صفحه نگاه می‌کند؛ Container Query به فضای Component.»**
- **«Container Query مکمل Media Query است، نه جایگزین مطلق آن.»**

### منابع رسمی این فصل

- Elementor Help: Responsive editing and inherited responsive values
- CSS Media Queries / CSS Containment specifications
- Elementor Help: Custom CSS per device and state

# ۱۵. درک عمیق RTL و Logical Properties؛ Start و End به‌جای حدس راست و چپ

## مسئله‌ای که RTL حل می‌کند

در یک صفحهٔ فارسی، جهت نوشتن از راست به چپ است. اما Layout فقط متن نیست. فاصله، Icon، Border، Position و ترتیب بصری نیز باید با جهت سند سازگار باشند.

اگر طراحی را فقط با `left` و `right` بسازی، ممکن است:

- نسخهٔ انگلیسی برعکس شود؛
- Icon سمت نادرست بماند؛
- Marginها در RTL و LTR نیازمند دو CSS جدا شوند؛
- Component قابل استفاده مجدد نباشد.

---

## تشبیه به دنیای واقعی: درِ ورودی و خروجی

فرض کن یک سالن دو در دارد، اما به‌جای اینکه بگویی «در سمت راست»، می‌گویی:

- درِ شروع مسیر
- درِ پایان مسیر

در سالن فارسی، شروع از راست است. در سالن انگلیسی، شروع از چپ.

Logical Propertyها نیز به‌جای مختصات فیزیکی، نقش جهت را بیان می‌کنند.

```text
LTR: inline-start = left
RTL: inline-start = right
```

---

## محور Inline و Block

در نوشتار معمول افقی:

- Inline Axis مسیر حرکت متن است.
- Block Axis مسیر روی‌هم‌قرارگرفتن سطرها و پاراگراف‌هاست.

برای فارسی:

```text
Inline: از راست به چپ
Block: از بالا به پایین
```

Logical Propertyها با این دو محور کار می‌کنند.

---

## تبدیل‌های مهم

| Physical Property | Logical Property | معنی |
|---|---|---|
| `margin-left/right` | `margin-inline-start/end` | فاصله در آغاز/پایان مسیر متن |
| `padding-left/right` | `padding-inline-start/end` | فضای داخلی آغاز/پایان |
| `top/bottom` | `inset-block-start/end` | جای‌گذاری در محور Block |
| `left/right` | `inset-inline-start/end` | جای‌گذاری در محور Inline |
| `width` | `inline-size` | اندازه در مسیر Inline |
| `height` | `block-size` | اندازه در مسیر Block |
| `border-left/right` | `border-inline-start/end` | Border منطقی |

این جایگزینی همیشه اجباری نیست؛ گاهی واقعاً «سمت فیزیکی چپ صفحه» منظور است. اما برای Componentهای جهت‌پذیر، Logical Property معمولاً بیان بهتری است.

---

## `direction` چیست و چه چیزی نیست؟

`direction: rtl` جهت پایهٔ متن و بعضی رفتارهای Inline را تعیین می‌کند. اما نباید از آن برای برعکس‌کردن تصادفی Layout استفاده کنی.

برای Flexbox:

- `direction` سند روی Start/End اثر دارد.
- `flex-direction` محور و ترتیب Flex را تعیین می‌کند.

این دو را با هم قاطی نکن.

```text
Document direction = زبان و جریان نوشتن
Flex direction = جهت چیدمان Itemها در Container
```

---

## محتوای دوطرفه یا Bidi

در متن فارسی ممکن است این موارد کنار هم باشند:

```text
نسخه 4.1.3
CSS: flex: 1 1 0
example.com/path
شماره 0912...
```

الگوریتم Bidi مرورگر تلاش می‌کند ترتیب نمایش را درست کند، اما عبارت‌های Inline با جهت متفاوت گاهی نیاز به Isolation دارند.

برای متن Dynamic ناشناخته، `dir="auto"` یا Elementهایی مانند `bdi` می‌توانند کمک کنند. هدف این است که جهت یک عبارت خارجی، ترتیب جملهٔ اطراف را خراب نکند.

---

## در Elementor V4

برای طراحی فارسی:

1. زبان و `dir` سند را درست تنظیم کن.
2. Alignment را با نقش محتوا انتخاب کن، نه فقط با عادت «همه‌چیز راست».
3. Utility Classهای فاصله را Logical بساز.
4. Badgeهای Absolute را با `inset-inline-start/end` قرار بده.
5. Icon و متن Button را در RTL و LTR آزمایش کن.
6. Dynamic Tagهای عددی، URL و عنوان‌های ترکیبی را بررسی کن.

مثال Utility:

```css
.u-space-after {
  margin-inline-end: 1rem;
}
```

همین Class در RTL و LTR معنای «بعد از عنصر» را حفظ می‌کند.

---

## Flexbox و Start/End

در `row`، Main Start به Direction نوشتار وابسته است. در صفحهٔ RTL، Row از سمت راست آغاز می‌شود. اما `row-reverse` ترتیب Main Axis را دوباره برعکس می‌کند.

به‌جای حفظ‌کردن چهار حالت، محور را روی کاغذ بکش:

```text
RTL + row:          ← مسیر دیداری از start راست به end چپ
RTL + row-reverse:  → برعکس همان محور
```

ترتیب DOM و ترتیب دیداری را نیز جدا بررسی کن؛ Reverse کردن Layout نباید معنای محتوا یا ترتیب Focus را خراب کند.

---

## اشتباهات رایج

- `text-align: right` به‌عنوان راه‌حل تمام RTL
- استفاده از Margin Left/Right برای Component قابل ترجمه
- تغییر `direction` برای جابه‌جایی یک Icon
- استفاده افراطی از `row-reverse`
- ندیدن ترتیب Focus و Screen Reader
- ترکیب عدد، URL و فارسی بدون تست Bidi
- ترجمهٔ UI بدون تغییر `lang` و `dir`

---

## پل به DevTools

در Elements Panel مقدارهای `dir` و `lang` را روی Ancestorها ببین. سپس در Computed Style این موارد را بررسی کن:

```text
direction
writing-mode
margin-inline-*
padding-inline-*
inset-inline-*
text-align
flex-direction
```

اگر یک Property منطقی به مقدار فیزیکی تبدیل شده، Computed Style جهت نهایی را نشان می‌دهد.

---

## تصویر ذهنی نهایی

به‌جای گفتن «سمت راست سالن»، بگو «ابتدای مسیر». راست و چپ با زبان عوض می‌شوند؛ Start و End نقش خود را حفظ می‌کنند.

---

## قوانین طلایی

- **«RTL فقط راست‌چین‌کردن متن نیست؛ جهت یک قرارداد سراسری است.»**
- **«برای Component قابل‌حمل، Start و End از Left و Right معنایی‌ترند.»**
- **«`direction` سند و `flex-direction` دو مسئولیت متفاوت دارند.»**
- **«Reverse دیداری را با ترتیب معنایی DOM اشتباه نگیر.»**
- **«فارسی، عدد، URL و کد را کنار هم آزمایش کن.»**

### منابع رسمی این فصل

- CSS Logical Properties and Values
- W3C Internationalization guidance for inline bidi markup
- CSS Flexible Box Layout specification

# ۱۶. درک عمیق State؛ Normal، Hover، Focus، Focus Visible و Active

## مسئله‌ای که State حل می‌کند

یک Button فقط یک مستطیل ثابت نیست. کاربر باید بفهمد:

- آیا قابل کلیک است؟
- آیا Pointer روی آن قرار دارد؟
- آیا با Keyboard به آن رسیده است؟
- آیا همین لحظه فشرده شده است؟
- آیا انتخاب شده یا Disabled است؟

State زبان بازخورد رابط است.

---

## تشبیه به دنیای واقعی: دکمهٔ آسانسور

دکمهٔ آسانسور همیشه همان دکمه است، اما وضعیتش تغییر می‌کند:

- Normal: منتظر است.
- Hover: دست به آن نزدیک شده است.
- Focus: اکنون مقصد ورودی Keyboard است.
- Focus Visible: چراغ راهنما زمانی روشن شده که کاربر برای پیدا کردن موقعیتش به آن نیاز دارد.
- Active: انگشت دقیقاً در حال فشار دادن است.
- Selected: انتخابی پایدارتر ثبت شده است.

Element عوض نشده؛ شرایط تعامل عوض شده است.

---

## Normal

Normal پایهٔ ظاهری Element است. Stateهای دیگر باید تغییر معناداری نسبت به آن بسازند، نه اینکه تمام طراحی را از نو تعریف کنند.

مثلاً Button پایه:

```text
Background: brand-primary
Text: on-primary
Border: transparent
```

---

## Hover

Hover وقتی Pointer روی Element قرار می‌گیرد فعال می‌شود.

هدف:

> نشان دادن امکان تعامل پیش از کلیک.

اما Hover نباید تنها راه نمایش اطلاعات ضروری باشد، چون:

- Touch Deviceها Hover واقعی ندارند؛
- کاربر Keyboard ممکن است هرگز آن را نبیند؛
- Hover پیچیده می‌تواند باعث Layout Shift شود.

تغییر رنگ، Shadow یا Transform کوچک معمولاً بهتر از تغییر Size و Flow است.

---

## Focus

Focus یعنی ورودی بعدی Keyboard یا تعامل به این Element مربوط است.

Input هنگام تایپ، Button هنگام ناوبری با Tab و Link هنگام انتخاب Keyboard Focus می‌گیرند.

حذف کامل Outline بدون جایگزین، کاربر Keyboard را بی‌نقشه می‌کند.

---

## Focus Visible

`:focus-visible` تلاش می‌کند Indicator را زمانی نشان دهد که مرورگر تشخیص می‌دهد کاربر احتمالاً به آن نیاز دارد؛ معمولاً در ناوبری Keyboard.

این راهی برای تعادل میان زیبایی و Accessibility است، نه مجوز حذف Focus.

الگوی رایج:

```css
.button:focus-visible {
  outline: 3px solid currentColor;
  outline-offset: 3px;
}
```

---

## Active

Active کوتاه‌ترین State است؛ لحظهٔ بین Press و Release.

یک Transform کوچک می‌تواند حس فشرده‌شدن بدهد:

```css
.button:active {
  transform: translateY(1px);
}
```

اما Active نباید تنها نشانه ثبت عمل باشد. بعد از کلیک ممکن است Loading، Success یا Error نیز لازم باشد.

---

## State روی Class، نه فقط Element

در Elementor V4، State را برای Class انتخاب‌شده ویرایش می‌کنی. این نکته بسیار مهم است:

```text
Global Class button-primary + Hover
```

یعنی Hover تمام Elementهایی را که از همان Global Class استفاده می‌کنند تغییر می‌دهد.

```text
Local Class + Hover
```

یعنی استثنای همان Element.

پس قبل از تغییر State نگاه کن کدام Class فعال است.

---

## تعارض Stateها و Style Ghosting

وقتی رنگ Normal را تغییر می‌دهی اما Button خاصی تغییر نمی‌کند، این زنجیره را بررسی کن:

```text
Breakpoint فعلی؟
State فعلی؟
Local Class مقدار دارد؟
Global Class دیگری بالاتر است؟
Custom CSS برای Hover/Focus وجود دارد؟
```

ممکن است Property در Hover صریحاً تعریف شده باشد و تغییر Normal هنگام Hover دیده نشود.

Indicatorهای V4 می‌توانند نشان دهند مقدار از Local، Global یا Class رقیب آمده است. روی Indicator کلیک کن و منبع Style را پیدا کن؛ نام دقیق دکمه Reset را از UI نسخه هدف بخوان و مقدار صریح را پاک کن.

---

## در Elementor V4

سناریوی Button:

```text
button-base
├── Normal: structure, typography, radius
├── Hover: background shift + subtle shadow
├── Focus Visible: clear outline
└── Active: small press feedback
```

اگر `button-base` Global است، Stateهای عمومی نیز همان‌جا قرار می‌گیرند. اگر فقط یک CTA خاص رفتار متفاوت دارد، Local Class یا Variant Pattern بررسی می‌شود.

---

## Accessibility

State خوب فقط زیبا نیست:

- Contrast کافی دارد.
- Focus Indicator واضح است.
- تغییر فقط با رنگ منتقل نمی‌شود، اگر معنا مهم باشد.
- Reduced Motion را در Animationهای State رعایت می‌کند.
- Disabled را از Normal قابل تشخیص می‌کند.
- Hover اطلاعات حیاتی را انحصاری نمی‌کند.

---

## پل به DevTools

در Styles Panel روی `:hov` کلیک کن و Stateهای زیر را Force کن:

```text
:hover
:active
:focus
:focus-visible
```

این روش اجازه می‌دهد Style State را بدون نگه‌داشتن موس یا Keyboard بررسی کنی.

---

## اشتباهات رایج

- حذف Outline بدون جایگزین
- طراحی فقط Hover
- تغییر Width یا Padding در Hover و تکان‌دادن Layout
- ویرایش Hover روی Local Class در حالی که قصد Global داری
- تعریف رنگ‌های متعارض در چند Class
- استفاده از Active به‌جای Loading Feedback
- فرض Hover واقعی در Mobile

---

## تصویر ذهنی نهایی

State لباس تازهٔ Element نیست؛ حالت چهرهٔ همان Element در یک لحظه است. Hover قصد نزدیک‌شدن، Focus مرکز توجه و Active لحظهٔ فشار است.

---

## قوانین طلایی

- **«State وضعیت موقت است، نه Element جدید.»**
- **«Hover برای Pointer است؛ Focus برای ناوبری؛ Focus Visible برای راه‌یابی قابل دسترس.»**
- **«Focus را حذف نکن؛ آن را درست طراحی کن.»**
- **«State را روی Class درست و Breakpoint درست ویرایش کن.»**
- **«بازخورد State نباید Layout را بلرزاند.»**

# ۱۷. درک عمیق Design System؛ رابطهٔ Variable، Class و Component

## مسئله‌ای که Design System حل می‌کند

بدون سیستم، سایت پر از تصمیم‌های مشابه اما ناهماهنگ می‌شود:

```text
سبز #004526
سبز #004627
سبز #014526
Padding 30px
Padding 32px
Padding 34px
```

هر مقدار به‌تنهایی ممکن است «تقریباً درست» باشد، اما کل سایت به‌مرور زبان مشترک خود را از دست می‌دهد.

Design System فقط مجموعه رنگ‌ها نیست؛ **نقشهٔ تصمیم‌های قابل استفاده مجدد** است.

---

## تشبیه به دنیای واقعی: آشپزخانهٔ زنجیره‌ای

یک رستوران زنجیره‌ای را تصور کن:

- Ingredient Standard = Variable؛ مثلاً سس اصلی یا وزن نمک
- Recipe = Global Class؛ ترکیب مواد و روش ارائه
- Dish Template = Component؛ ساختار کامل غذا
- Local Adjustment = Local Class؛ استثنای همان بشقاب

اگر قیمت نمک عوض شود، Recipe را از نو نمی‌نویسی. اگر شکل کامل غذا تکرار می‌شود، فقط رنگ بشقاب را کپی نمی‌کنی؛ Template لازم است.

---

## سه سؤال اصلی

### آیا فقط یک مقدار مشترک است؟

```text
#004526
1.5rem
8px
```

→ Variable

### آیا یک بسته Style روی Elementهای مختلف تکرار می‌شود؟

```text
Typography + Color + Padding + Border
```

→ Global Class

### آیا یک ساختار چندElementی با رابطه و رفتار مشترک تکرار می‌شود؟

```text
Card
├── Image
├── Title
├── Price
└── Button
```

→ Component

تعداد تکرار علامت است، نه قانون. ممکن است یک Brand Color از همان روز اول Variable باشد، حتی اگر هنوز فقط دو مصرف دارد.

---

## Token Tiering؛ از ماده خام تا نقش

در Design Systemهای مدرن می‌توان سه سطح مفهومی دید:

```text
Primitive Token
purple-500 = #6D5DFB
        ↓
Semantic Token
brand-primary = purple-500
        ↓
Component Token
button-background = brand-primary
```

### Primitive

مقدار خام را نام‌گذاری می‌کند.

### Semantic

نقش مقدار را توضیح می‌دهد.

### Component Token

مصرف آن در Component خاص را بیان می‌کند.

این مدل از نظر معماری بسیار مفید است، اما نباید بدون شواهد ادعا کرد Elementor فعلی زنجیره Variable-to-Variable چندسطحی را Native پشتیبانی می‌کند. در پیاده‌سازی مطمئن می‌توان زنجیره را چنین ساخت:

```text
Variable معنایی
↓
Global Class Property
↓
Component Style
```

پشتیبانی Alias Chain باید با Export واقعی نسخه هدف تأیید شود.

---

## چرا نام معنایی بهتر است؟

```text
green-900
```

رنگ را توصیف می‌کند.

```text
surface-brand
```

نقش را توصیف می‌کند.

اگر برند از سبز به آبی تغییر کند، نام `green-900` در صدها مصرف دروغ می‌شود، اما `surface-brand` هنوز درست است.

Primitive و Semantic هر دو می‌توانند مفید باشند؛ مهم این است که نقش هر Tier روشن باشد.

---

## Base + Variant

یک الگوی معماری مفید:

```text
card-base
card-featured
card-dark
```

- Base مسئول Style مشترک است.
- Variant فقط تفاوت معنادار را اضافه می‌کند.

اما «Variant» یک مفهوم معماری است، نه الزاماً Entity رسمی جدا در Elementor. باید با Global Class و رفتار واقعی Component نسخه هدف آزمایش شود.

قانون ساده:

> Component برای ساختار تکراری، Class برای ظاهر تکراری و Variable برای مقدار تکراری است.

این قانون راهنماست، نه دیوار آهنی. Component Style پایه نیز دارد و Global Class ممکن است بخشی از معماری Component باشد.

---

## Utility Class در کنار Design System

Utilityها ابزارهای کوچک‌اند:

```text
u-flex-center
u-text-center
u-full-width
u-space-block-lg
```

آن‌ها نباید جای Component و Semantic Class را بگیرند. اگر یک Card از ده Utility نامفهوم تشکیل شود، درک قصد طراحی سخت می‌شود.

تعادل:

```text
Semantic Class برای هویت
Utility Class برای تغییر کوچک و روشن
Variable برای مقدار مرکزی
```

---

## در Elementor V4

Design System Panel و Class/Variables Manager محل مدیریت مرکزی‌اند. برای هر تصمیم بپرس:

```text
آیا این مقدار باید هم‌زمان در کل سایت تغییر کند؟
آیا این Style روی نوع‌های مختلف Element تکرار می‌شود؟
آیا این ساختار باید از یک Master پیروی کند؟
آیا این فقط استثنای یک Element است؟
```

همچنین V3 Global Colors/Fonts و V4 Variables می‌توانند در فرایند Hybrid نیازمند Sync باشند. Sync را با یکسان‌بودن کامل مدل‌ها اشتباه نگیر.

---

## نقشهٔ وابستگی

قبل از تغییر یک Variable یا Class مرکزی، دامنه اثر را ببین:

```text
brand-primary
├── button-primary
│   ├── Header CTA
│   └── Pricing CTA
├── link-default
└── badge-featured
```

هرچه Dependency مرکزی‌تر است، تغییر آن باید با نمونه‌های نماینده آزمایش شود.

---

## اشتباهات رایج

- Variable برای هر عدد یک‌بارمصرف
- Global Class با مسئولیت‌های نامرتبط
- Component برای دو Element صرفاً هم‌رنگ
- نام‌های ظاهری بدون معنا
- ساخت Variantهای متعدد بدون Base روشن
- Alias Chain فرضی بدون تست
- تبدیل همه‌چیز به Utility و از دست‌دادن Intent
- تغییر Token مرکزی بدون بررسی مصرف‌کنندگان

---

## تصویر ذهنی نهایی

Variable مادهٔ اولیه است، Class دستور پخت و Component قالب کامل سرو غذا. اگر این سه را جابه‌جا کنی، آشپزخانه پر از نسخه‌های کپی و دستورهای متناقض می‌شود.

---

## قوانین طلایی

- **«Variable مقدار را تکرار می‌کند؛ Class Style را؛ Component ساختار را.»**
- **«نام معنایی نقش را حفظ می‌کند، حتی اگر مقدار عوض شود.»**
- **«تعداد مصرف معیار کمکی است، نه قانون قطعی سیستم‌سازی.»**
- **«Variant الگوی معماری است؛ آن را قابلیت Native اثبات‌نشده معرفی نکن.»**
- **«هر تصمیم مرکزی یک دامنه اثر دارد؛ پیش از تغییر، مصرف‌کنندگان را ببین.»**

### منابع رسمی این فصل

- Elementor Help: Variables, Variables Manager, Classes and Components
- Elementor Help: Import/export design systems and V3/V4 synchronization
- Design Tokens Community Group material for conceptual token architecture

# ۱۸. درک عمیق Hybrid V3/V4؛ مهاجرت بدون بازسازی کور

## مسئله‌ای که مهاجرت حل می‌کند

یک سایت واقعی ممکن است شامل این موارد باشد:

- Widgetهای V3
- Atomic Elementهای V4
- Add-onهای شخص ثالث
- Custom CSS وابسته به DOM قدیمی
- Dynamic Tagها
- فرم‌ها
- Templateهای Theme Builder
- صفحه‌های تجاری حساس

مهاجرت یک دکمهٔ «قدیمی را جدید کن» نیست. مهاجرت مدیریت ریسک است.

---

## تشبیه به دنیای واقعی: بازسازی بیمارستان در حال کار

یک بیمارستان را نمی‌توان یک‌شبه تعطیل و از نو ساخت. بعضی بخش‌ها جدید می‌شوند، بعضی موقتاً قدیمی می‌مانند و مسیرهای اتصال باید حفظ شوند.

- V3 = بال قدیمی اما فعال
- V4 = بال جدید
- Hybrid = راهروی اتصال
- Staging = ماکت و محیط آزمایش
- Rollback = مسیر بازگشت اضطراری

هدف فقط نوکردن ساختمان نیست؛ خدمات باید حین تغییر ادامه پیدا کند.

---

## هم‌زیستی V3 و V4

مستندات رسمی V4 تصریح می‌کنند Elementهای V4 و Widgetهای 3.x می‌توانند در یک صفحه کنار هم استفاده شوند.

این یعنی وجود هر دو ساختار به‌خودی‌خود خطا نیست. Hybrid یک مرحلهٔ معتبر است.

اما هم‌زیستی می‌تواند مسائل تازه بسازد:

- دو مدل Style
- Global Colors/Fonts در برابر Variables
- DOM متفاوت
- کنترل‌های Responsive متفاوت
- رفتار Add-onها
- Custom CSS وابسته به Selector قدیمی

---

## ماتریس تصمیم مهاجرت

### سؤال ۱: Feature Parity وجود دارد؟

آیا Element V4 تمام قابلیت لازم Widget قدیمی را دارد؟

### سؤال ۲: وابستگی شخص ثالث چیست؟

Add-on، Script، Tracking یا Custom JS به Markup قدیمی وابسته است؟

### سؤال ۳: صفحه چقدر حساس است؟

صفحهٔ پرداخت یا Landing Page پرفروش نیازمند آزمایش و Rollback قوی‌تر است، نه لزوماً ممنوعیت مهاجرت.

### سؤال ۴: Baseline داریم؟

قبل از تغییر:

- Screenshot
- Core Web Vitals/Lab Metrics
- رفتار فرم
- مسیر Keyboard
- Dynamic Data
- Conversion events

ثبت شده‌اند؟

### خروجی تصمیم

```text
Keep V3
Hybridize
Pilot one section
Rebuild new page in V4
Full migration after verification
```

---

## چه زمانی Pilot مناسب است؟

یک Section کم‌ریسک انتخاب کن که:

- ساختار تکرارشونده دارد؛
- Add-on پیچیده ندارد؛
- Dynamic Data حساس ندارد؛
- در چند Viewport قابل مقایسه است.

آن را در V4 بازسازی کن و نتیجه را با نسخه قبلی مقایسه کن.

---

## چرا «V4 همیشه سریع‌تر است» ادعای خوبی نیست؟

Atomic Architecture می‌تواند DOM و Style System ساده‌تری بسازد، اما Performance نهایی به پیاده‌سازی بستگی دارد:

- تعداد Elementها
- تصاویر
- Scriptها
- Interactions
- Fontها
- Add-onها
- Server
- Cache

پس باید Benchmark کرد، نه اینکه از نام نسخه نتیجه گرفت.

---

## Sync میان مدل‌های Design System

V3 از Global Colors/Fonts و V4 از Variables/Classes استفاده می‌کند. Elementor امکان Sync برخی Variableها با Global Assets را ارائه می‌کند.

اما Sync به این معنی نیست که تمام قابلیت‌ها و دامنه‌ها یکسان‌اند. مثلاً محدودیت نوع Variable یا ویژگی‌های Typography باید طبق نسخه هدف بررسی شود.

---

## Custom CSS و DOM قدیمی

Selector زیر ممکن است به Markup خاص V3 وابسته باشد:

```css
.elementor-widget-container > .some-inner-wrapper
```

اگر V4 Wrapperها یا Classها را تغییر دهد، CSS می‌شکند.

قبل از مهاجرت، Custom CSS را دسته‌بندی کن:

```text
Selector پایدار و معنایی
Selector وابسته به DOM داخلی
!importantهای زیاد
JS querySelector وابسته به Class قدیمی
```

---

## مسیر عملی مهاجرت

```text
Inventory
↓
Dependency Map
↓
Baseline
↓
Pilot
↓
Visual/Functional/Accessibility/Performance Regression
↓
Rollback test
↓
مرحله بعد
```

هر workaround باید نسخه، تاریخ، Plugin و شرایط بازتولید داشته باشد. Workaround بدون نسخه به‌سرعت تبدیل به افسانه می‌شود.

- Custom CSS ظاهر و رفتار CSS را تعریف می‌کند.
- HTML Attribute اطلاعات و معنا به Markup می‌افزاید.
- Dynamic Tag مقدار را از دادهٔ سایت می‌آورد.

اگر این سه را مخلوط کنی، ممکن است Style را داخل داده، رفتار را داخل Class نامناسب یا محتوای پویا را در HTML ثابت پنهان کنی.

---

## تشبیه به دنیای واقعی: لباس، برچسب هویت و پرونده

یک کارمند را تصور کن:

- لباس و ظاهر او = CSS
- کارت شناسایی و مشخصات روی آن = Attribute
- اطلاعاتی که از پایگاه داده شرکت می‌آید = Dynamic Data

لباس نمی‌گوید شماره پرسنلی چیست. کارت شناسایی رنگ کت را تعیین نمی‌کند. پرونده نیز جای طراحی لباس نیست.

---

## Custom CSS

Custom CSS وقتی لازم است که کنترل بصری پنل کافی نیست یا یک رفتار استاندارد CSS پیشرفته می‌خواهی:

```css
text-wrap: balance;
container-type: inline-size;
```

در V4، Custom CSS می‌تواند به Class، State و Device مرتبط باشد. پس قبل از نوشتن کد، Class فعال را بررسی کن.

Custom CSS نباید اولین واکنش به هر مشکل باشد. اگر Layout با Flex/Grid Control قابل حل است، CSS اضافی ممکن است منبع دوم حقیقت بسازد.

---

## Attributes

Attribute بخشی از HTML است:

```html
<button aria-expanded="false" data-panel="pricing">
```

کاربردها:

- `id`
- `data-*`
- `aria-*`
- `rel`
- `target`
- Hook برای JavaScript یا Testing

Attribute باید معنای درست و مقدار معتبر داشته باشد. افزودن ARIA اشتباه می‌تواند Accessibility را بدتر کند.

قانون:

> ARIA جای Element معنایی بومی را نمی‌گیرد.

اگر Button لازم است، Div با `role="button"` راه‌حل اول نیست.

---

## Dynamic Tag

Dynamic Tag مقدار را از Context می‌آورد:

```text
Post Title
Product Price
Featured Image
Author Name
Custom Field
Site URL
```

همان Template در صفحه‌های مختلف مقدار متفاوت می‌گیرد.

Dynamic Data یعنی Layout باید برای ناشناخته‌ها آماده باشد:

- مقدار خالی
- متن کوتاه
- متن بسیار بلند
- تصویر ناموجود
- قیمت چندخطی
- URL طولانی

---

## Dynamic Data و معماری Empty State

`empty-cells` راه‌حل Grid یا Flex برای داده خالی نیست؛ این Property به Table Cell مربوط است.

برای Element Dynamic بپرس:

```text
اگر داده خالی باشد، خود Element Render می‌شود؟
Wrapper خالی باقی می‌ماند؟
Gap Parent همچنان اعمال می‌شود؟
Fallback داریم؟
Display Condition لازم است؟
```

مثال کارت مقاله:

```text
Card
├── Featured Image (optional)
├── Category (optional)
├── Title (required)
└── Excerpt (optional)
```

اگر Category خالی است، پنهان‌کردن Text Element ممکن است کافی نباشد؛ اگر Wrapper جدا دارد، Gap یا Height آن نیز باید بررسی شود.

---

## Display Conditions

Display Condition می‌تواند Element را براساس شرط نشان دهد یا پنهان کند. این با CSS `display:none` دستی یکسان نیست؛ رفتار Render، DOM و Frontend باید در نسخه هدف بررسی شود.

شرط‌های Dynamic برای وجود یا نبود مقدار می‌توانند از Wrapper خالی جلوگیری کنند، اما نباید بدون تست نتیجه‌گیری کرد که همه Gapها یا Markupها حذف می‌شوند.

---

## AI کجای این معماری قرار می‌گیرد؟

AI ابزار Authoring است:

- متن پیشنهاد می‌دهد؛
- تصویر تولید می‌کند؛
- Form یا Tabs اولیه می‌سازد؛
- CSS پیشنهاد می‌کند.

اما پس از تولید، معماری Runtime همچنان از Element، Class، Variable، Dynamic Data و Component تشکیل می‌شود.

AI منبع حقیقت معماری نیست. خروجی آن باید مانند کد و طراحی انسانی Audit شود.

---

## در Elementor V4

مثال Button Dynamic:

```text
Text: Dynamic Product Title
Link: Dynamic Product URL
Class: button-primary
Attribute: aria-label / data-tracking-id در صورت نیاز معتبر
Custom CSS: فقط رفتار اضافی اثبات‌شده
```

هر لایه مسئولیت خودش را دارد.

---

## تست محتوای پویا

حداقل این Fixtureها را ببین:

```text
عنوان ۱۰ کاراکتری
عنوان ۱۲۰ کاراکتری فارسی
بدون تصویر
تصویر عمودی
قیمت کوتاه
قیمت با تخفیف و چند مقدار
فیلد اختیاری خالی
URL طولانی
```

Layoutی که فقط با یک Post نمونه درست است، هنوز Dynamic-ready نیست.

---

## اشتباهات رایج

- Custom CSS برای حل Tree اشتباه
- استفاده از Attribute غیراستاندارد بدون `data-`
- ARIA نادرست
- Dynamic Data بدون Fallback
- فرض حذف کامل Wrapper خالی
- استفاده از `:empty` بدون توجه به Whitespace و Markup
- مخلوط‌کردن AI با Runtime Data
- اعتماد به یک نمونه محتوا

---

## تصویر ذهنی نهایی

CSS لباس است، Attribute کارت شناسایی و Dynamic Tag پرونده‌ای است که از بانک اطلاعاتی می‌آید. هر سه روی یک فرد اثر دارند، اما جای یکدیگر را نمی‌گیرند.

---

## قوانین طلایی

- **«CSS ظاهر را می‌سازد؛ Attribute معنا و Hook را؛ Dynamic Tag مقدار را.»**
- **«Dynamic Layout را با داده خالی و متن بلند آزمایش کن.»**
- **«Fallback و Display Condition بخشی از معماری محتوا هستند.»**
- **«ARIA اشتباه از نبود ARIA هم می‌تواند بدتر باشد.»**
- **«AI نقطه شروع تولید است، نه مهر تأیید معماری.»**

# ۲۰. درک عمیق Interactions؛ Trigger، Effect و زمان‌بندی

## مسئله‌ای که Interaction حل می‌کند

Interaction می‌گوید وقتی رویدادی رخ داد، Element چگونه واکنش نشان دهد.

```text
رویداد → واکنش
```

بدون این تفکیک، Animationها به حرکت‌های تزئینی پراکنده تبدیل می‌شوند و معلوم نیست چرا، چه زمانی و برای چه کاربری اجرا می‌شوند.

---

## تشبیه به دنیای واقعی: زنگ، حسگر و موتور

یک در اتوماتیک را تصور کن:

- Trigger = حسگر حضور
- Effect = بازشدن در
- Duration = مدت بازشدن
- Delay = فاصله میان تشخیص و شروع
- Direction = مسیر حرکت
- Repeat/Timeline = الگوی تکرار یا پیشرفت

اگر حسگر اشتباه باشد، بهترین موتور هم در زمان نادرست کار می‌کند.

---

## Trigger چیست؟

Trigger لحظهٔ آغاز است. در Interactions رسمی Elementor نمونه‌هایی مانند این‌ها وجود دارند:

- Page Load
- Scroll Into View
- While Scrolling
- Hover
- Click

هر Trigger پیامد متفاوتی دارد.

Page Load بدون قصد کاربر اجرا می‌شود. Click به تصمیم کاربر وابسته است. While Scrolling ممکن است بار محاسباتی بیشتری ایجاد کند.

---

## Effect چیست؟

Effect تغییر دیداری است:

- Fade
- Slide
- Scale
- Transformهای دیگر

Effect باید معنای تجربه را پشتیبانی کند. اگر محتوای اصلی فقط پس از Animation قابل فهم است، Progressive Enhancement ضعیف شده است.

---

## Duration و Delay

Duration طول حرکت است. Delay زمان انتظار پیش از شروع.

Animation بسیار کند، رابط را سنگین می‌کند. Animation بسیار سریع ممکن است دیده نشود. Delay زیاد برای محتوای اصلی حس خرابی می‌دهد.

به‌جای عدد جادویی، از نقش حرکت شروع کن:

```text
Micro feedback: کوتاه
Entrance support: متوسط و محدود
Storytelling sequence: با احتیاط و تست
```

---

## Interactions و Deviceها

مستندات رسمی فعلی می‌گویند Interactions روی تمام Deviceها اعمال می‌شوند و برای Screen Sizeهای مختلف قابل شخصی‌سازی نیستند.

پس Interactionی که در Desktop خوب است باید روی Touch، Mobile و دستگاه کم‌توان نیز آزمایش شود.

Hover Trigger روی Touch مفهوم متفاوت یا محدود دارد. طراحی نباید اطلاعات حیاتی را به Hover وابسته کند.

---

## Reduced Motion

بعضی کاربران حرکت کمتر را در سیستم درخواست می‌کنند.

```css
@media (prefers-reduced-motion: reduce) {
  /* حرکت را حذف یا بسیار محدود کن */
}
```

اگر کنترل Native Interaction این Preference را پوشش نمی‌دهد، باید رفتار واقعی نسخه هدف بررسی و در صورت نیاز راهکار مکمل طراحی شود.

---

## INP و Main Thread

Interaction سنگین می‌تواند پاسخ کلیک را عقب بیندازد:

```text
Click
↓
JavaScript طولانی
↓
Style recalculation
↓
Layout
↓
Paint
↓
Next frame دیر نمایش داده می‌شود
```

INP فقط مدت Animation نیست؛ تأخیر از ورودی تا Paint بعدی را می‌سنجد. تعداد زیاد Handlerها، DOM بزرگ و Layout Thrashing می‌توانند پاسخ را کند کنند.

---

## در Elementor V4

برای هر Interaction یک قرارداد بنویس:

```text
Element: Pricing Card
Trigger: Click
Effect: Expand details
Purpose: reveal optional information
Fallback: content accessible without motion
Duration: 200ms
Reduced motion: no transform
```

از Animation به‌عنوان ادویه استفاده کن، نه غذای اصلی.

---

## چند Interaction روی یک Element

وقتی چند Interaction ترکیب می‌شوند، ترتیب و تعارض مهم است:

- Hover Scale
- Click Slide
- Scroll Fade

همه ممکن است Transform را تغییر دهند و روی یکدیگر سایه بیندازند. منبع Transform نهایی را در Computed Style و Timeline بررسی کن.

---

## اشتباهات رایج

- Animation برای هر Element
- Page Load Animation روی محتوای حیاتی
- Hover-only behavior
- Delay طولانی
- Transformهای متعارض
- نادیده‌گرفتن Reduced Motion
- فرض Device-specific بودن Interactions
- اندازه‌گیری نکردن INP و Long Task
- استفاده از Animation برای پنهان‌کردن Layout Shift

---

## پل به DevTools

در Performance Panel یک Interaction ضبط کن. این موارد را ببین:

```text
Event timing
Long tasks
Style recalculation
Layout
Paint
Frames
```

در Elements Panel نیز Transform و Transition نهایی را بررسی کن.

---

## تصویر ذهنی نهایی

Interaction مثل در اتوماتیک است. Trigger حسگر است و Effect موتور. اگر هرکس از جلوی ساختمان رد شد ده موتور هم‌زمان روشن شوند، مشکل از زیبایی در نیست؛ از معماری واکنش است.

---

## قوانین طلایی

- **«Trigger می‌گوید چه وقت؛ Effect می‌گوید چه تغییر کند.»**
- **«Animation ادویه است، نه غذای اصلی.»**
- **«محتوا بدون حرکت نیز باید قابل فهم و قابل دسترسی باشد.»**
- **«Interaction را روی Mobile، Touch و Reduced Motion آزمایش کن.»**
- **«حرکت زیبا اگر پاسخ کلیک را کند کند، تجربه خوب نیست.»**

### منابع رسمی این فصل

- Elementor Help: Interactions
- Elementor Developers: Editor 4.0 interactions update
- web.dev: Interaction to Next Paint guidance
- CSS prefers-reduced-motion

# ۲۱. درک عمیق Atomic Form؛ فرم به‌عنوان ساختار و جریان وضعیت

## مسئله‌ای که Atomic Form حل می‌کند

فرم فقط چند Input کنار هم نیست. فرم یک جریان ارتباطی است:

```text
کاربر اطلاعات می‌دهد
↓
اعتبارسنجی می‌شود
↓
ارسال می‌شود
↓
Success یا Error رخ می‌دهد
```

اگر فقط ظاهر Input را طراحی کنی، ممکن است Label، Error، Focus و پیام نتیجه فراموش شوند.

---

## تشبیه به دنیای واقعی: باجهٔ اداره

یک باجه را تصور کن:

- Form Wrapper = خود باجه
- Label = عنوان هر بخش فرم
- Input = کادر اطلاعات
- Required = مدارک اجباری
- Validation = بررسی مأمور
- Submit = تحویل پرونده
- Success = رسید پذیرش
- Error = اعلام نقص پرونده

باجه زیبا بدون راهنمای درست، مردم را سردرگم می‌کند.

---

## چرا Atomic؟

در مدل Atomic، Form Wrapper شامل Elementهای مستقل‌تر است:

```text
Atomic Form
├── Label + Input
├── Label + Select
├── Checkbox
├── Submit Button
├── Success Message
└── Error Message
```

این ساختار کنترل بیشتری بر Layout و Style می‌دهد، اما مسئولیت بیشتری نیز دارد. طراح باید ارتباط معنایی Fieldها، IDها، Labelها و پیام‌ها را درست نگه دارد.

---

## State Machine فرم

در مستندات رسمی فعلی Appearanceهای اصلی Form شامل این حالت‌هاست:

```text
Normal
├── Success
└── Error
```

از نظر مفهومی، در زمان ارسال یک وضعیت Pending/Submitting نیز وجود دارد، اما پشتیبانی Native آن به‌عنوان Appearance قابل Style در منابع رسمی بررسی‌شده اثبات نشده است.

پس دو سطح را جدا کن:

### وضعیت‌های رسمی قابل استناد

- Normal
- Success
- Error

### نیاز UX پیشنهادی و نیازمند بررسی پیاده‌سازی

- Submitting/Pending
- Disabled Submit
- Busy Indicator
- جلوگیری از ارسال تکراری

---

## Label و Input

Placeholder جای Label نیست.

Placeholder با تایپ ناپدید می‌شود و ممکن است Contrast کمی داشته باشد. Label باید مشخص کند Field چیست.

اتصال Label و Input معمولاً با `for` و `id` انجام می‌شود. IDهای Field باید یکتا و قابل پیش‌بینی باشند.

---

## Validation

پیام Error باید:

- نزدیک Field مربوط باشد؛
- فقط با رنگ منتقل نشود؛
- قابل فهم باشد؛
- مسیر اصلاح را بگوید؛
- در صورت امکان برای Screen Reader اعلام شود.

بد:

```text
Invalid input
```

بهتر:

```text
شماره تلفن باید ۱۱ رقم باشد.
```

---

## Focus Management

پس از Error، کاربر باید بفهمد کجا مشکل دارد. در فرم طولانی، انتقال Focus به خلاصه خطا یا اولین Field نامعتبر می‌تواند مفید باشد، اما رفتار واقعی باید با ابزار و پیاده‌سازی موجود سنجیده شود.

پس از Success نیز پیام نتیجه باید قابل مشاهده و قابل اعلام باشد.

`aria-live` می‌تواند در بعضی سناریوها برای پیام نتیجه مناسب باشد، اما افزودن آن باید با Markup واقعی و بدون تکرار مزاحم آزمایش شود.

---

## در Elementor V4

برای هر Form این نقشه را بساز:

```text
Purpose
Fields
Required fields
Validation messages
Submit action
Success behavior
Error behavior
Email/collection action
Privacy text
Keyboard path
```

Appearanceهای Normal، Success و Error را جدا طراحی کن. Success Message و Fail Message را حذف نکن یا صرفاً به رنگ وابسته نکن.

---

## Layout فرم

در Desktop ممکن است دو Field کنار هم باشند:

```text
[نام] [نام خانوادگی]
```

در Mobile:

```text
[نام]
[نام خانوادگی]
```

Parent Layout باید اجازه دهد Label و Error همراه Field خود بمانند. Grid برای فرم‌های چندستونه مفید است، ولی ترتیب DOM باید با مسیر منطقی Tab سازگار بماند.

---

## Dynamic و Conditional Form

اگر Fieldها براساس انتخاب قبلی نمایش داده می‌شوند:

- Required بودن Field مخفی را بررسی کن.
- ترتیب Focus را آزمایش کن.
- Error مربوط به Field پنهان نباید کاربر را گیر بیندازد.
- Layout نباید با نمایش Field جدید جهش نامفهوم داشته باشد.

این رفتارها ممکن است به Add-on یا قابلیت‌های خارج از Atomic Form پایه وابسته باشند و باید نسخه‌محور مستند شوند.

---

## اشتباهات رایج

- Placeholder به‌جای Label
- Error فقط قرمز
- Success Message نامشخص
- Field ID تکراری
- ترتیب دیداری مخالف ترتیب Tab
- نبود Feedback هنگام ارسال
- چندبار ارسال‌شدن Form
- پنهان‌کردن Error با Overflow
- فرض وجود State Native Submitting بدون شواهد
- ادعای Dynamic Class رسمی برای Stateهای Form بدون Fixture

---

## پل به DevTools و Accessibility Tree

- با Tab کل Form را طی کن.
- Label مرتبط را در Accessibility Tree ببین.
- Stateهای Error و Success را در Frontend واقعی اجرا کن.
- Network request، Response و Disabled شدن Button را بررسی کن.
- فقط Preview ظاهری کافی نیست.

---

## تصویر ذهنی نهایی

فرم باجهٔ اداری است. Inputها فقط کاغذها هستند؛ تجربهٔ واقعی را راهنما، بررسی، رسید موفقیت و توضیح خطا می‌سازند.

---

## قوانین طلایی

- **«Form یک جریان وضعیت است، نه مجموعه‌ای از کادرها.»**
- **«Placeholder جای Label را نمی‌گیرد.»**
- **«Error باید قابل فهم، قابل یافتن و قابل اصلاح باشد.»**
- **«Normal، Success و Error را جدا طراحی و آزمایش کن.»**
- **«Submitting نیاز واقعی UX است، اما قابلیت Native آن را بدون سند قطعی فرض نکن.»**

### منابع رسمی این فصل

- Elementor Help: Atomic Form element
- WAI guidance for form labels, errors and keyboard focus
- Elementor Help: V4 elements and form actions

# ۲۲. درک عمیق Component، Master و Instance

## مسئله‌ای که Component حل می‌کند

فرض کن یک Pricing Card در دوازده صفحه داری. همهٔ آن‌ها ساختار یکسانی دارند:

```text
Badge
Title
Price
Feature List
Button
```

اگر هر Card یک کپی مستقل باشد، تغییر ساختار باید دوازده بار انجام شود. یکی از نسخه‌ها جا می‌ماند و سایت به‌تدریج ناهماهنگ می‌شود.

Component برای تکرار کنترل‌شدهٔ **ساختار و Style پایه** ساخته شده است.

---

## تشبیه به دنیای واقعی: نقشهٔ مادر ساختمان

یک شرکت ساختمانی یک نقشهٔ مادر برای شعبه‌های خود دارد.

- Master Component = نقشهٔ اصلی
- Instance = شعبه‌ای که با آن نقشه ساخته شده
- Exposed Property = بخش‌هایی که مدیر شعبه اجازه دارد تغییر دهد، مثل نام، تصویر یا لینک
- Propagation = رسیدن اصلاح نقشه به تمام شعبه‌ها
- Detach = اعلام اینکه این شعبه از این پس مستقل است و دیگر نقشهٔ مرکزی را دنبال نمی‌کند

اگر دیوار اصلی در نقشه جابه‌جا شود، همهٔ شعبه‌ها تحت تأثیرند. اگر فقط نام روی تابلو عوض شود، لازم نیست نقشهٔ ساختمان تغییر کند.

---

## Master چه چیزی را مالک است؟

Master معمولاً این موارد را کنترل می‌کند:

- ساختار Elementها
- ترتیب آن‌ها
- Style پایه
- Classها و Variableهای پایه
- Propertyهایی که اجازهٔ سفارشی‌سازی دارند
- حذف یا افزودن بخش‌ها

تغییر Master دامنهٔ سراسری دارد و باید با احتیاط منتشر شود.

---

## Instance چه چیزی را مالک است؟

Instance مقدار Propertyهایی را کنترل می‌کند که Master صریحاً Expose کرده است.

مستندات فعلی Elementor می‌گویند تنظیمات واجد آیکون Property در General Tab می‌توانند در Master به‌عنوان Property قابل سفارشی‌سازی ارائه شوند. متن و تصویر مثال‌های رایج‌اند، اما فهرست فقط به آن‌ها محدود نیست.

تصویر:

```text
Master: Team Card
├── Photo → exposed
├── Name → exposed
├── Role → exposed
├── Link → exposed
└── Layout/Style → synchronized
```

هر Instance عکس و نام خودش را دارد، اما ساختار و Style پایه را از Master می‌گیرد.

---

## Propagation؛ سرایت تغییر

تغییر Master مثل ویرایش نقشهٔ مرکزی است. اگر Padding، ترتیب Elementها یا Button Style را عوض کنی، همه Instanceها تغییر می‌کنند.

پیش از تغییر Master، نمونه‌های نماینده را بررسی کن:

```text
Instance با متن کوتاه
Instance با متن بلند فارسی
Instance در Container باریک
Instance در Desktop
Instance در Mobile
Instance با تمام Overrideهای مجاز
```

عدد ثابت «پنج نمونه» قانون نیست؛ مهم پوشش حالت‌های متفاوت است.

---

## Detach چیست؟

Detach ارتباط Instance با Master را قطع می‌کند. پس از Detach، ساختار مستقل می‌شود و تغییرات Master را دریافت نمی‌کند.

Detach برای استثنای واقعی معتبر است. اما اگر برای تغییر رایجی مثل رنگ یا Label دائماً Instanceها را Detach می‌کنی، این یک **بوی معماری** است:

- شاید Property مناسب Expose نشده؛
- شاید Variant Class لازم است؛
- شاید Variable یا Global Class در محل درست نیست؛
- شاید واقعاً دو Component متفاوت داری.

قانون درست این نیست که «Detach همیشه اشتباه است». قانون درست این است:

> Detach باید تصمیم آگاهانه برای استقلال باشد، نه میانبر روزمره برای دورزدن Master.

---

## Base + Variant

فرض کن Pricing Card دو ظاهر دارد:

```text
Normal
Featured
```

اگر ساختار یکی است و فقط Surface، Border یا Badge فرق دارد، ساخت دو Master جدا ممکن است تکرار غیرضروری باشد.

الگوی معماری:

```text
Component: pricing-card
Class پایه: card-base
Variant Class: card-featured
```

اما باید در نسخه هدف تأیید شود که افزودن Class به Instance یا Root آن بدون Detach چگونه ذخیره می‌شود و پس از تغییر Master باقی می‌ماند. بنابراین Variant Class یک الگوی پیشنهادی است، نه Entity رسمی اثبات‌شده‌ای به نام Variant در Elementor.

---

## Slot چیست و چرا نباید با قطعیت به Elementor نسبت داده شود؟

در معماری عمومی Component، Slot محل خالی کنترل‌شده‌ای است که مصرف‌کننده می‌تواند محتوای دلخواه در آن قرار دهد.

```text
Card Component
├── Header Slot
├── Body Slot
└── Footer Slot
```

اما در مستندات رسمی فعلی Components Elementor، قابلیت مشخص و قراردادی با نام Slot اثبات نشده است.

پس می‌توان Slot را به‌عنوان مفهوم عمومی آموزش داد، اما نباید نوشت:

> Componentهای V4 حتماً Slot Native دارند.

---

## Component چه زمانی مناسب نیست؟

- فقط یک مقدار رنگ تکرار شده → Variable
- فقط Style یک Button تکرار می‌شود → Global Class
- فقط یک Wrapper ساده در یک صفحه وجود دارد → شاید Component لازم نیست
- دو Card ساختار و رفتار کاملاً متفاوت دارند → شاید دو Component مستقل بهتر باشند

Component بیش از حد، Dependency Graph بزرگی می‌سازد و تغییرات مرکزی را پرریسک می‌کند.

---

## در Elementor V4

فرایند فکری:

```text
آیا ساختار تکرار می‌شود؟
↓ بله
آیا تفاوت Instanceها قابل تعریف و محدود است؟
↓ بله
Master بساز
↓
Propertyهای ضروری را Expose کن
↓
Instanceهای نماینده را آزمایش کن
↓
تغییر Master را با دامنه اثر منتشر کن
```

Master را در یک صفحهٔ تصادفی و بدون دیدن مصرف‌کنندگان تغییر نده.

---

## اشتباهات رایج

- ساخت Master جدا برای هر رنگ
- Expose کردن همه تنظیمات و از بین بردن انسجام
- Expose نکردن محتوای لازم و مجبورکردن Detach
- تغییر Master بدون بررسی Instanceهای بلند و باریک
- فرض رسمی بودن Slot یا Variant
- استفاده از Component برای یک Value
- Detach بدون ثبت دلیل
- ساخت Component تو‌در‌تو بدون نقشه Dependency

---

## تصویر ذهنی نهایی

Master نقشهٔ مادر است و Instance شعبه. Exposed Property پنجره‌ای است که مدیر شعبه اجازه دارد تغییر دهد. Detach یعنی شعبه از زنجیره جدا شده است؛ آزادی بیشتری می‌گیرد، اما دیگر به‌روزرسانی مرکزی دریافت نمی‌کند.

---

## قوانین طلایی

- **«Master ساختار و Style پایه را کنترل می‌کند؛ Instance فقط Propertyهای Exposeشده را.»**
- **«تغییر Master، تغییر محلی نیست؛ دامنهٔ سراسری دارد.»**
- **«Detach برای استثناست، نه برای هر تغییر رایج.»**
- **«تفاوت صرفاً ظاهری را پیش از Component دوم، با Class و Variable بررسی کن.»**
- **«Slot و Variant را بدون سند به‌عنوان قابلیت Native Elementor معرفی نکن.»**

# ۲۳. درک عمیق Variable و Design Token؛ مقدار نام‌دار با دامنهٔ اثر

## مسئله‌ای که Variable حل می‌کند

در یک سایت بزرگ، مقدارهای مشترک در صدها Property مصرف می‌شوند:

```text
رنگ برند
Font اصلی
فاصله استاندارد
Radius
اندازه عنوان
```

اگر مقدار خام را در همه‌جا تکرار کنی، تغییر آن دشوار و ردیابی مصرف‌ها مبهم می‌شود.

Variable یک مقدار نام‌دار و مرکزی می‌سازد.

---

## تشبیه به دنیای واقعی: شمارهٔ تماس مرکزی

فرض کن روی صد بروشور شماره مستقیم یک کارمند چاپ شده است. با تغییر کارمند، باید همه بروشورها را عوض کنی.

اگر به‌جای شماره مستقیم نوشته باشد:

```text
تماس با پشتیبانی مرکزی
```

و سیستم مرکزی شماره واقعی را نگه دارد، فقط یک نقطه تغییر می‌کند.

Variable همین لایهٔ ارجاع است:

```text
brand-primary → #004526
```

مصرف‌کننده نام را می‌شناسد؛ مقدار از Registry می‌آید.

---

## Value و Reference را جدا کن

این دو یکسان نیستند:

```text
Observed value: #004526
Saved reference: brand-primary
```

در Editor ممکن است رنگ نهایی را ببینی، اما سند در واقع Reference را ذخیره کند. این تفکیک برای Export، Migration و Debugging بسیار مهم است.

اگر Variable حذف شود، Reference ممکن است Unresolved شود. نباید مقدار قبلی را بی‌صدا حدس زد.

---

## نام‌گذاری Primitive و Semantic

### Primitive

```text
color-green-900
space-6
radius-2
```

ساختار Scale را توصیف می‌کند.

### Semantic

```text
color-brand-primary
space-section-inline
radius-card
```

نقش را توصیف می‌کند.

هر دو سطح مفیدند. Primitive برای Palette و Scale، Semantic برای Intent.

---

## Token Tiering

مدل مفهومی:

```text
Primitive
green-900 = #004526
       ↓
Semantic
brand-primary = green-900
       ↓
Component use
button background = brand-primary
```

این زنجیره ذهن سیستم‌ساز را قوی می‌کند، اما پشتیبانی Variable-to-Variable Reference در Elementor باید با Export واقعی نسخه هدف تأیید شود.

راه مطمئن‌تر تا زمان اثبات:

```text
Variable معنایی
↓
Global Class
↓
Component
```

---

## Variable چه چیزی نیست؟

Variable مجموعه Style نیست.

```text
card-surface = background + padding + border + shadow
```

این دیگر یک Value ساده نیست؛ Global Class یا Component Style مناسب‌تر است.

Variable همچنین ساختار تولید نمی‌کند.

---

## دامنهٔ اثر

تغییر Variable مرکزی ممکن است ده‌ها مصرف‌کننده را تغییر دهد.

```text
space-lg
├── Section Padding
├── Card Gap
├── Form Row Gap
└── Header Height calculation
```

اگر یک Variable در نقش‌های نامرتبط استفاده شده باشد، تغییر آن باعث اثرهای ناخواسته می‌شود. به این وضعیت Coupling پنهان می‌گوییم.

مثلاً استفاده از یک Variable به نام `space-32` در همه‌جا شاید ساده باشد، اما اگر بعداً Section Padding باید 40 و Card Gap باید 24 شود، نقش‌ها از هم جدا می‌شوند.

Semantic Token این Coupling را آشکارتر می‌کند.

---

## Type Compatibility

هر Variable برای هر Property مناسب نیست. Color، Font Family و Size نوع‌های متفاوتی دارند.

دسترسی Variableها نیز ممکن است به نسخه، Plan و Property وابسته باشد. مستندات فعلی باید برای قابلیت دقیق نسخه هدف بررسی شوند؛ نباید فرض کرد هر Property Effects، Shadow یا Layout حتماً Variable می‌پذیرد.

---

## در Elementor V4

Variables Manager محل ساخت و مدیریت Variableهاست. هنگام استفاده:

1. نقش Variable را نام‌گذاری کن.
2. Type آن را درست انتخاب کن.
3. مصرف‌کنندگان نماینده را ثبت کن.
4. پیش از Delete، Referenceهای وابسته را پیدا کن.
5. در Hybrid V3/V4، Sync با Global Colors/Fonts را جداگانه بررسی کن.
6. Export Design System را برای انتقال Variables و Classes استفاده کن، اما ZIP را به‌عنوان شواهد نسخه‌دار نگه دار.

---

## چه زمانی Variable نسازیم؟

یک مقدار یک‌بارمصرف که هویت معنایی و نیاز تغییر مرکزی ندارد، لزوماً Variable نمی‌خواهد.

مثال:

```text
offset تزئینی خاص یک Illustration = 13px
```

اگر فقط در همان Stage معنا دارد، Local Value می‌تواند خواناتر باشد.

هدف حذف تمام Literalها نیست؛ هدف مدیریت تصمیم‌های مشترک است.

---

## اشتباهات رایج

- Variable برای هر عدد
- نام‌گذاری فقط با رنگ فعلی
- استفاده یک Token برای نقش‌های نامرتبط
- حذف Variable بدون بررسی Referenceها
- فرض زنجیره Alias بدون شواهد
- فرض پشتیبانی همه Propertyها
- Sync V3/V4 بدون درک محدودیت‌ها
- استفاده از Variable به‌جای Global Class

---

## تصویر ذهنی نهایی

Variable شمارهٔ تماس مرکزی است. اگر هر بروشور شماره خام خودش را چاپ کند، تغییر پرهزینه است. اما اگر همه به دفتر مرکزی اشاره کنند، تغییر یکجا انجام می‌شود—به شرطی که دفتر مرکزی نقش‌های نامرتبط را با یک شماره قاطی نکرده باشد.

---

## قوانین طلایی

- **«Variable یک Value نام‌دار است، نه بسته Style.»**
- **«Reference و مقدار Resolveشده را دو چیز جدا بدان.»**
- **«نام معنایی دامنهٔ تغییر را روشن می‌کند.»**
- **«هر Variable مرکزی یک Dependency Graph دارد.»**
- **«Alias Chain و پشتیبانی Propertyها را با نسخه واقعی تأیید کن.»**

- Elementor Help: Variables and Variables Manager
- Elementor Help: Import/export design systems
- Elementor Help: Sync variables and global elements

# ۲۴. درک عمیق Class Manager؛ سلسله‌مراتب سیستم Style

## مسئله‌ای که Class Manager حل می‌کند

در یک سایت Classمحور، مشکل فقط ساخت Class نیست. باید بدانی:

- چه Classهایی وجود دارند؛
- کجا مصرف شده‌اند؛
- کدام یک اولویت بالاتری دارد؛
- کدام خالی یا بدون استفاده است؛
- تغییر نام یا حذف چه دامنه‌ای دارد.

Class Manager دفتر ثبت قوانین ظاهری سایت است.

---

## تشبیه به دنیای واقعی: آیین‌نامه‌های سازمان

یک سازمان چند سطح قانون دارد:

- قانون عمومی شرکت
- آیین‌نامه واحد
- دستور خاص یک کارمند

اگر دو آیین‌نامه درباره لباس تعارض داشته باشند، باید ترتیب اولویت معلوم باشد.

در Elementor V4:

- Local Class مانند دستور خاص همان Element است.
- Global Class قانون قابل استفاده در چند Element است.
- Class Manager ترتیب رقابت Global Classها را مدیریت می‌کند.

---

## Priority در Class Manager

مستندات رسمی فعلی می‌گویند Class سمت چپ/بالاتر اولویت بیشتری از Class سمت راست/پایین دارد و Local Class همیشه بیشترین اولویت را می‌گیرد.

Drag & Drop در Class Manager ترتیب Global Classها را تغییر می‌دهد.

این Priority را با Specificity عددی CSS یکی ندان. Elementor ممکن است CSS را با Source Order یا سازوکار داخلی طوری تولید کند که این قرارداد اجرا شود.

---

## Resolution Tree

وقتی Property نهایی را می‌بینی، این مسیر را بررسی کن:

```text
Device/Breakpoint
↓
State
↓
Class فعال برای ویرایش
↓
Local Class explicit value
↓
Global Classهای متصل و Priority Registry
↓
Custom CSS همان Class/State/Device
↓
CSS Cascade مرورگر
↓
Computed Style
```

این یک مدل عیب‌یابی است. ترتیب دقیق همه لایه‌های Custom CSS و Generated CSS باید در موارد حساس با DevTools و Fixture نسخه هدف تأیید شود.

---

## Indicatorهای Style

رابط V4 برای منبع یا تعارض Style Indicatorهای رنگی نشان می‌دهد. در مستندات فعلی:

- Pink با Local Value مرتبط است.
- Green نشان می‌دهد Class فعال برنده است.
- Gray نشان می‌دهد مقدار از منبع دیگری می‌آید.
- Orange نشان می‌دهد مقدار Class حاضر Override شده است.

با کلیک روی Indicator می‌توان منبع Style و Styleهای نادیده‌گرفته‌شده را دید.

رنگ و رفتار UI ممکن است در نسخه‌های بعدی تغییر کند؛ بنابراین Screenshot نسخه و تاریخ بررسی را در جزوه نگه دار.

---

## ردیابی شبح Style

فرض کن `button-primary` را سبز کرده‌ای اما یک Button هنوز نارنجی است.

### مرحله ۱: State

آیا روی Hover هستی و Hover مقدار نارنجی دارد؟

### مرحله ۲: Breakpoint

آیا Mobile Override جدا دارد؟

### مرحله ۳: Local Class

آیا Local Class همان Button رنگ صریح دارد؟

### مرحله ۴: Global Class رقیب

آیا `button-warning` نیز متصل است و Priority بالاتری دارد؟

### مرحله ۵: Custom CSS

آیا Selector اختصاصی یا `!important` وجود دارد؟

### مرحله ۶: Computed Style

کدام Rule واقعاً برنده شده است؟

این الگوریتم از حدس‌زدن جلوگیری می‌کند.

---

## Utility Classes در Class Manager

Utilityها را با نام‌گذاری روشن نگه دار:

```text
u-flex-center
u-inline-full
u-overflow-clip
u-space-block-lg
```

اگر تعداد Utilityهای متعارض زیاد شود، Class Manager تبدیل به میدان جنگ Priority می‌شود.

مثلاً هم‌زمان‌کردن این کلاس‌ها مبهم است:

```text
u-gap-sm
u-gap-lg
u-gap-none
```

بهتر است در هر Element فقط یک Utility از هر مسئولیت متعارض فعال باشد.

---

## Filter و Audit

Class Manager می‌تواند برای پیدا کردن Classهای:

- روی همین صفحه
- بدون استفاده
- خالی

مفید باشد.

اما «بدون استفاده» باید با احتیاط تفسیر شود؛ ممکن است Class در Template، Dynamic Context یا صفحه دیگری مصرف شود. دامنهٔ Filter را بخوان.

در برخی حالت‌های Filter، Drag & Drop در دسترس نیست؛ برای تغییر ترتیب باید Filter را برداری.

---

## Rename و Delete

# ۲۵. درک عمیق Refactor؛ تغییر ساختار بدون گم‌کردن رفتار

## مسئله‌ای که Refactor حل می‌کند

یک صفحه ممکن است ظاهراً درست باشد اما پشت آن:

- Wrapperهای اضافی
- Classهای تکراری
- Valueهای خام پراکنده
- Custom CSSهای جبرانی
- Duplicateهای Desktop/Mobile
- Componentهای مشابه

وجود داشته باشد.

Refactor یعنی ساختار داخلی را بهتر کنی، بدون اینکه رفتار مورد انتظار را ناخواسته بشکنی.

---

## تشبیه به دنیای واقعی: بازسازی لوله‌کشی بدون قطع آب

خانه کار می‌کند، اما لوله‌ها پیچیده و تکه‌تکه‌اند. Refactor یعنی مسیر لوله را ساده کنی، اتصالات اضافی را حذف کنی و شیرهای مرکزی بسازی—درحالی‌که آب باید همچنان به همه اتاق‌ها برسد.

ظاهر یکسان کافی نیست. فشار آب، ایمنی و تعمیرپذیری نیز باید حفظ شوند.

---

## Refactor با Redesign فرق دارد

### Refactor

```text
هدف: حفظ رفتار، بهبود ساختار
```

### Redesign

```text
هدف: تغییر تجربه یا ظاهر
```

اگر هنگام حذف Wrapper، فاصله یا ترتیب Mobile را عمداً تغییر می‌دهی، شاید کار دیگر Refactor خالص نیست. تغییرات را نام‌گذاری کن تا دامنه کار مبهم نشود.

---

## نقشه Refactor

### تکرار Value

```text
#004526 در 18 نقطه
```

→ Variable را بررسی کن.

### تکرار Style

```text
همان Button Style در 12 Element
```

→ Global Class را بررسی کن.

### تکرار Structure

```text
همان Card Tree در 8 صفحه
```

→ Component را بررسی کن.

### Wrapper بدون مسئولیت

```text
Div فقط یک Child دارد و Layout/Style/Meaning نمی‌دهد
```

→ حذف آزمایشی را بررسی کن.

---

## Wrapper چه زمانی اضافی نیست؟

Wrapper ممکن است مسئولیت واقعی داشته باشد:

- Layout Parent
- Containing Block
- Stacking Context
- Clip/Overflow Stage
- Background Layer
- Semantic Group
- Container Query Context
- Interaction Target

پس «هر Wrapper کمتر بهتر» قانون ناقصی است.

از خودت بپرس:

> اگر این Wrapper را حذف کنم، کدام مسئولیت بی‌صاحب می‌شود؟

اگر جواب «هیچ» است، کاندید حذف است.

---

## روش امن Refactor

```text

↓

↓
Visual comparison
↓

↓

↓

↓

```

چند Refactor بزرگ را هم‌زمان انجام نده؛ پیدا کردن علت Regression سخت می‌شود.

---

## Baseline چیست؟

پیش از تغییر ثبت کن:

- Screenshot عرض‌های اصلی
- Computed Style Elementهای حساس
- ترتیب DOM
- مسیر Keyboard
- Form behavior
- Dynamic data cases
- Performance trace یا حداقل Metric پایه

Baseline حافظه قابل اعتماد است؛ ذهن انسان جزئیات فاصله و رفتار را دقیق نگه نمی‌دارد.

---

## Local به Global

اگر یک Local Style در چند محل تکرار شده، فقط Copy/Paste نکن. Intent مشترک را پیدا کن.

بد:

```text
همه سبز و 16px هستند، پس یک Class
```

بهتر:

```text
همه Action Link اصلی‌اند، پس action-link-primary
```

شباهت عددی همیشه به معنای هویت مشترک نیست.

---

## Variant Extraction

دو Component تقریباً یکسان‌اند:

```text

Card Dark
```

اگر فقط Surface و Text Color فرق دارند، Base + Variant Class را بررسی کن.

اگر Structure، Interaction یا Property Contract فرق دارد، ادغام ممکن است معماری را پیچیده‌تر کند.

---

ابزارهای مفید:

- DevTools برای CSS واقعی

Refactor را فقط در Editor انجام نده؛ Frontend و Data Dynamic را نیز بررسی کن.

---

## اشتباهات رایج

- حذف Wrapper فقط برای کاهش Node
- ادغام Classهای صرفاً هم‌رنگ
- ساخت Variable برای هر Literal
- تبدیل همه چیز به Component
- Refactor و Redesign هم‌زمان
- تغییر Master بدون Baseline
- اعتماد به Screenshot Desktop
- حذف Class «بدون استفاده» بدون بررسی دامنه
- ادعای بهبود Performance بدون اندازه‌گیری

---

## تمرین علت‌یابی معکوس

روی Duplicate صفحه، هر بار یک خطای کنترل‌شده بساز:

```text

```

سپس بدون نگاه فوری به نسخه سالم، علت شکست را با Tree و Computed Style توضیح بده. هدف خراب‌کردن پروژه نیست؛ هدف دیدن مسئولیت هر قطعه است.

---

## تصویر ذهنی نهایی

Refactor بازسازی لوله‌کشی خانه‌ای است که هنوز باید آب داشته باشد. حذف هر لوله خوب نیست؛ فقط لوله‌ای را حذف کن که مسئولیتی ندارد یا مسیرش با سیستم مرکزی جایگزین شده است.

---

## قوانین طلایی

- **«Refactor رفتار را حفظ می‌کند؛ Redesign رفتار را تغییر می‌دهد.»**
- **«هر Wrapper را با مسئولیتش قضاوت کن، نه فقط با تعداد Node.»**
- **«شباهت عددی لزوماً هویت مشترک نیست.»**
- **«یک تغییر کوچک، یک مقایسه روشن.»**
- **«بدون Baseline، Refactor قابل اثبات نیست.»**

# ۲۶. درک عمیق Performance، DOM و Audit؛ ساده‌سازی قابل اندازه‌گیری

## مسئله‌ای که Performance حل می‌کند

Performance فقط امتیاز Lighthouse نیست. کاربر تجربه می‌کند:

- محتوای اصلی چه زمانی دیده می‌شود؛
- صفحه هنگام Load چقدر می‌پرد؛
- کلیک چقدر زود پاسخ می‌گیرد؛
- Scroll و Animation چقدر روان‌اند.

سه معیار اصلی Core Web Vitals این تجربه را از سه زاویه می‌بینند:

```text
LCP: محتوای اصلی چه زمانی دیده شد؟
INP: تعامل چقدر زود پاسخ دید؟
CLS: صفحه چقدر بی‌اجازه جابه‌جا شد؟
```

---

## تشبیه به دنیای واقعی: رستوران

- LCP = غذای اصلی چه زمانی روی میز رسید؟
- INP = وقتی گارسون را صدا زدی، چه زمانی پاسخ داد؟
- CLS = آیا میز و صندلی هنگام نشستن ناگهان جابه‌جا شدند؟

رستورانی که دکور سبک دارد اما غذا دیر می‌رسد، سریع نیست. سایتی با DOM کم اما Hero Image سنگین نیز لزوماً سریع نیست.

---

## آستانه‌های راهنما

برای تجربه خوب، راهنمای فعلی Core Web Vitals معمولاً این هدف‌ها را مطرح می‌کند:

```text
LCP ≤ 2.5s
INP ≤ 200ms
CLS ≤ 0.1
```

ارزیابی Field باید در صدک ۷۵ و جداگانه برای Mobile/Desktop دیده شود.

این اعداد هدف‌اند، نه تضمین رتبه و نه جایگزین تحلیل کاربر واقعی.

---

## LCP

LCP زمان نمایش بزرگ‌ترین Image یا Text Block مهم در Viewport اولیه را می‌سنجد.

علت‌های رایج مشکل:

- Hero Image بزرگ
- Lazy Load اشتباه روی LCP Image
- کشف دیر Resource
- Server Response کند
- Font یا CSS مسدودکننده
- Client-side rendering دیر

برای Image اصلی:

- اندازه مناسب
- `srcset/sizes`
- Width/Height
- اولویت درست
- فرمت مناسب

را بررسی کن.

---

## CLS

CLS جابه‌جایی غیرمنتظره Layout را می‌سنجد.

علت‌ها:

- Image بدون ابعاد
- Embed بدون فضای رزروشده
- Font Swap شدید
- Dynamic Banner که بالای محتوا ظاهر می‌شود
- Componentی که پس از Load ارتفاعش تغییر می‌کند
- Animation روی Layout Property

`aspect-ratio` یا Width/Height به رزرو فضای Image کمک می‌کند.

---

## INP

INP تأخیر کلی Interactionهای کاربر را در طول بازدید می‌سنجد.

علت‌ها:

- JavaScript Long Task
- Event Handler سنگین
- DOM بزرگ
- Style Recalculation گسترده
- Layout Thrashing
- Interactionهای زیاد
- Third-party Script

Animation طولانی لزوماً INP بد نمی‌سازد؛ مهم این است که پس از Input، Frame بعدی چقدر دیر آماده شود.

---

## DOM Size؛ معیار تشخیصی، نه حکم جهانی

DOM بزرگ می‌تواند Memory، Style Recalculation و Layout را گران‌تر کند.

Lighthouse در Audit قدیمی/تشخیصی DOM Size از حدود ۸۰۰ Node برای هشدار و حدود ۱۴۰۰ برای وضعیت شدید استفاده کرده است، اما این اعداد قانون جهانی کیفیت نیستند.

نباید نوشت:

```text
همیشه زیر 1000 Node خوب است.
```

یک صفحه ۷۰۰ Node با Script سنگین می‌تواند کندتر از صفحه ۱۵۰۰ Node ساده باشد.

همچنین برای هر Wrapper هزینه ثابت ۰٫۱ms یا ۰٫۳ms وجود ندارد. هزینه به Tree، Selector، Device و تغییرات Runtime وابسته است.

---

## Component و Token چگونه غیرمستقیم اثر می‌گذارند؟

Component بد طراحی‌شده ممکن است:

- Wrapperهای تکراری بسازد؛
- Imageهای غیرضروری Load کند؛
- Interactionهای متعدد ثبت کند؛
- Variantهای مخفی را هم‌زمان Render کند.

Token بد طراحی‌شده مستقیماً LCP را کند نمی‌کند، اما می‌تواند:

- CSS متناقض و Overrideهای زیاد بسازد؛
- تغییرات Style گسترده ایجاد کند؛
- نگهداری را سخت کند.

رابطه را علّی و دقیق بیان کن، نه اینکه «Token بد = CLS» بنویسی.

---

## Performance Budget

برای پروژه Budget تعریف کن:

```text

```

Budget باید متناسب با پروژه و دستگاه هدف باشد. عددهای بدون محیط تست فقط شعارند.

# ۲۷. درک عمیق وزن Element؛ هزینه فقط تعداد Node نیست

## مسئله‌ای که «وزن Element» حل می‌کند

دو Element ممکن است هر دو یک Node باشند، اما هزینه یکسانی نداشته باشند:

- یک Div ساده
- Video با Player
- Form با Validation
- Carousel با JavaScript
- Image بزرگ
- SVG پیچیده
- Interaction وابسته به Scroll

پس شمارش Node فقط یکی از نشانه‌هاست.

---

## تشبیه به دنیای واقعی: کوله‌پشتی

در یک کوله ده وسیله داری:

```text
۵ جوراب
۱ لپ‌تاپ
۱ بطری آب
۱ کتاب سنگین
۲ مداد
```

تعداد وسایل ۱۰ است، اما وزن را نوع وسیله تعیین می‌کند.

Elementها نیز چند نوع وزن دارند.

---

## پنج نوع وزن

### ۱. وزن ساختاری

- تعداد Node
- عمق Nesting
- تعداد Child مستقیم
- Wrapperهای اضافی

### ۲. وزن Style

- Selectorهای پیچیده
- Overrideهای زیاد
- Effects و Filter
- Shadowهای سنگین
- Style Recalculation دامنه‌دار

### ۳. وزن Media

- Byte تصویر و Video
- ابعاد Decode
- تعداد Font و Weight
- SVG پیچیده

### ۴. وزن رفتار

- Event Listener
- Interaction
- Scroll Handler
- Timer
- Animation

### ۵. وزن وابستگی

- Third-party library
- Add-on
- Network request
- Dynamic query
- Form action

یک Element ممکن است در چند دسته سنگین باشد.

---

## Wrapper ساده همیشه بی‌هزینه نیست، اما همیشه بد هم نیست

یک Wrapper ساده معمولاً هزینه کمی دارد، ولی در مقیاس زیاد:

- DOM عمیق‌تر می‌شود؛
- Selector Matching و Layout پیچیده‌تر می‌شود؛
- Debug سخت‌تر می‌شود.

بااین‌حال Wrapperی که Containing Block، Grid Context یا Semantic Group می‌سازد مسئولیت واقعی دارد.

به‌جای «Node را حذف کن» بگو:

> مسئولیت را با کمترین ساختار لازم اجرا کن.

---

## Depth و Breadth

### Depth زیاد

```text
Div
└── Div
    └── Div
        └── Div
            └── Text
```

مسیر Layout و Debug را طولانی می‌کند.

### Childهای بسیار زیاد

یک Parent با صدها Child نیز Recalculation و مدیریت را سخت می‌کند.

هیچ عدد جهانی برای عمق یا تعداد Child وجود ندارد؛ Audit باید با صفحه واقعی انجام شود.

---

## Element پنهان

`display:none` ممکن است Paint و Layout آن Subtree را حذف کند، اما:

- Markup ممکن است همچنان در DOM باشد؛
- Data و Asset شاید قبلاً Load شده باشد؛
- Script ممکن است ثبت شده باشد؛
- Duplicateهای Mobile/Desktop نگهداری را دو برابر کنند.

پس Hidden بودن مساوی «بی‌هزینه بودن کامل» نیست.

---

## Interaction Weight

ده Element ساده با Scroll Interaction ممکن است از صد Div ثابت پرهزینه‌تر باشند.

هر Interaction را از این نظر بررسی کن:

```text
Trigger frequency
JavaScript work
Style changes
Layout changes
Paint area
Compositor-friendly transform/opacity
```

Transform و Opacity معمولاً برای Animation مناسب‌تر از Width/Height/Top/Left هستند، اما تضمین بی‌هزینه بودن ندارند.

---

## Media Weight

یک Hero Image ۴MB می‌تواند از صد Wrapper مهم‌تر باشد.

علاوه بر Network Bytes، Decode Size را نیز ببین. تصویر فشرده ممکن است روی Disk کوچک باشد اما پس از Decode حافظه زیادی بگیرد.

Font نیز وزن دارد:

- تعداد Family
- تعداد Weight
- Subset
- preload
- fallback

---

## Class و Token Weight

Class زیاد لزوماً Runtime کند نمی‌سازد، اما Architecture را سنگین می‌کند:

- تشخیص منبع Style سخت می‌شود؛
- Override زیاد می‌شود؛
- CSS تولیدشده رشد می‌کند؛
- تغییرات مرکزی پرریسک می‌شوند.

این «وزن شناختی و نگهداری» است، نه فقط CPU.

---

## ماتریس وزن

| Element | ساختاری | Media | Behavior | Dependency | توضیح |
|---|---:|---:|---:|---:|---|
| Div ساده | کم | صفر | صفر | کم | مگر در تکرار زیاد |
| Image | کم | متوسط/زیاد | کم | Media | اندازه و LCP مهم |
| SVG پیچیده | کم | متغیر | متغیر | Asset | Path/Filter مهم |
| Form | متوسط | کم | زیاد | Backend | Validation/Actions |
| Carousel | متوسط | متوسط | زیاد | JS | Interaction و Asset |
| Video | کم | بسیار زیاد | متوسط | Player/Network | Poster و Loading مهم |

این جدول راهنماست، نه Benchmark عددی.

---

## در Elementor V4

هنگام انتخاب Element فقط نپرس «چند Node می‌سازد؟» بپرس:

```text
چه Assetی Load می‌کند؟
چه Scriptی فعال می‌کند؟
چند State/Interaction دارد؟
آیا Wrapperهای داخلی دارد؟
آیا Dynamic Query اجرا می‌کند؟
آیا جایگزین اتمیک سبک‌تری وجود دارد؟
```

Atomic Element ممکن است Markup ساده‌تری داشته باشد، اما نتیجه باید با Frontend واقعی سنجیده شود.

---

## اشتباهات رایج

- تبدیل Performance به Node Count
- حذف Wrapperهای مسئول
- نادیده‌گرفتن Image و Font
- مخفی‌کردن Duplicateها به‌جای حذف معماری تکراری
- استفاده از Widget سنگین برای رفتار ساده
- Animation Layout-based
- Classهای زیاد و نامفهوم
- عددسازی میلی‌ثانیه برای هر Wrapper

---

## تصویر ذهنی نهایی

DOM تعداد وسایل کوله است، اما وزن واقعی را جنس وسایل تعیین می‌کند. یک Video می‌تواند از صد Div سنگین‌تر باشد و یک Wrapper کوچک می‌تواند ستون نگهدارندهٔ کل ساختار باشد.

# ۲۸. درک عمیق ساخت مستقل؛ از مسئله به تصمیم قابل دفاع

## مسئله‌ای که ساخت مستقل حل می‌کند

دانشجو ممکن است هر کنترل را بشناسد، اما هنگام دیدن Screenshot تازه نداند از کجا شروع کند.

ساخت مستقل یعنی بدون دنبال‌کردن کلیک‌های مدرس بتوانی:

- ساختار را استخراج کنی؛
- نقش هر Parent را توضیح بدهی؛
- موتور Layout را انتخاب کنی؛
- Responsive Contract بسازی؛
- تصمیم‌ها را آزمایش و دفاع کنی.

---

## تشبیه به دنیای واقعی: جراحی با نقشهٔ بدن

حفظ‌کردن اینکه «در این بیمار برش را اینجا بزن» مهارت عمومی نمی‌سازد. جراح باید بداند:

- هر عضو چه نقشی دارد؛
- چه چیزی به چه چیزی متصل است؛
- حذف یک بخش چه پیامدی دارد؛
- نشانه‌های خطا چیست.

ساخت مستقل نیز از مدل ذهنی می‌آید، نه از حافظهٔ محل دکمه‌ها.

---

## مرحله ۱: مشاهده را از تفسیر جدا کن

### مشاهده

```text
دو ستون دیده می‌شود.
تصویر از مرز کارت بیرون زده است.
چهار Node تزئینی اطراف تصویر هستند.
در Mobile تصویر زیر متن آمده است.
```

### تفسیر

```text
احتمالاً Parent Flex Row است.
احتمالاً Visual Stage Position Relative دارد.
Nodeها احتمالاً Absolute هستند.
```

تفسیر را حقیقت قطعی معرفی نکن تا در Tree یا DevTools تأیید شود.

---

## مرحله ۲: Content Inventory

قبل از Containerها، محتوا را فهرست کن:

```text
Eyebrow
Heading
Paragraph
Button group
Main image
Decorative nodes
Logo list
```

محتوا می‌گوید چه چیزهایی باید معنای مستقل داشته باشند.

---

## مرحله ۳: Grouping

عناصر را بر اساس مسئولیت گروه‌بندی کن:

```text
Hero
├── Copy Group
│   ├── Eyebrow
│   ├── Heading
│   ├── Paragraph
│   └── Actions
└── Visual Stage
    ├── Main Image
    └── Decorative Nodes
```

هر Wrapper باید یک پاسخ داشته باشد:

> چرا وجود داری؟

---

## مرحله ۴: Layout Engine

برای هر Parent انتخاب کن:

```text
Normal Flow
Flex
Grid
Positioned Stage
```

کمترین موتور لازم را انتخاب کن.

- یک ستون متن → Flow/Flex Column
- Copy و Visual → Flex Row یا Grid
- Card Matrix → Grid
- Badge روی Image → Absolute در Stage

---

## مرحله ۵: قرارداد اندازه

فقط Width وارد نکن. بنویس:

```text
Copy: basis/grow/shrink/min-width
Visual: basis/grow/shrink/aspect-ratio
Parent: max-width/padding/gap
```

اندازه‌ها باید رابطه‌ای باشند، نه مجموعه عددهای جدا.

---

## مرحله ۶: سیستم Style

برای هر تصمیم مشخص کن:

```text
Local Class?
Global Class?
Utility Class?
Variable?
Component?
Variant pattern?
```

مثال:

```text
Hero layout → Global Class اگر تکرارشونده
Brand color → Variable
CTA structure → Component در صورت تکرار ساختاری
Node offset خاص → Local value
```

---

## مرحله ۷: Responsive Contract

پیش از Device Mode بنویس:

```text
چه چیزی ثابت می‌ماند؟
چه چیزی Direction عوض می‌کند؟
چه چیزی Wrap می‌شود؟
چه چیزی Scale می‌شود؟
چه چیزی واقعاً حذف می‌شود؟
چه چیزی نباید Duplicate شود؟
```

سپس Overrideهای حداقلی بساز.

- Alt/Label
